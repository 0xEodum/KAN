# C3: basis expansion without stored derivative rows; GEMM fusion evaluated

Backlog item C3 (P1), stage B. Date: 2026-10-06, branch `cpp-foundation`. Baseline: `c7978ff`
(C9 closed; built in a separate worktree, `KAN-c3base/build-parity` and `build-fma`). Final:
`790a06b` + documentation (`build-b-c3`, parity build; `build-b-c3-fma`, performance build; both
with Python and benchmarks).

## Scope decision

C3 as written: a fused kernel that computes the basis in shared memory while loading the X
tile of the contraction, and recomputes `Phi'` in the backward pass instead of storing it
(the V and D tensors of `batch*inputs*terms` per layer). The C9 profile estimated 20-25% of the
256-wide FP32 step and about 6% of the 1024-wide step, **if** the fused kernels ran as fast as
the cuBLAS kernels they replace.

The work was split into two stages, and measured before either was adopted:

1. **Recompute `Phi'`, keep cuBLAS (adopted).** The forward `basis_kernel` writes only `Phi`;
   the backward finish evaluates the forward's formula on the layer input inside its staged
   tile and reduces it against `W = U*C`. No custom GEMM.
2. **Fuse the expansion into hand-written GEMMs (prototyped, not adopted).** A fused forward
   (basis evaluated into the A tile), and a fused input VJP (`W = U*C` with an epilogue that
   recomputes `Phi'` and reduces it, so `W` never reaches global memory). Both lose to cuBLAS
   plus the unfused kernels on the shapes that matter (below): the hand-written SIMT SGEMM core
   is 10-30% slower than cuBLAS/CUTLASS on these shapes, more than the memory round trips the
   fusion removes.

**Owner decision (2026-10-06): close C3 at stage 1.** The stage-2 prototypes and their
measurements are kept here ([prototypes](C3-bench/prototypes/)). Fusing at library speed would
need a CUTLASS-class GEMM (a new dependency, an owner decision); it is recorded as a possible
follow-up in the backlog journal, not as an open item.

## Change (stage 1)

`src/resident.cu`, FP32/TF32 executor, `BasisEdges` layers:

- `ExpansionPlan::stored_derivatives`: false when the three-plane staged tile fits
  (`recompute_derivatives`: not trainable, `stage_rows(terms, 3) > 0`, i.e. FP32 and at most
  85 terms). The plan then reserves no derivatives region.
- `basis_kernel` with `derivatives == nullptr` (staged path only) still evaluates `Phi'` into its
  stage (the formulas produce both) but writes only `Phi`.
- `backward_finish_kernel` takes a row source: `StoredDerivatives` (rows written by the forward,
  as before) or `RecomputedDerivatives<Kind>` (input pointer and device basis view). The
  recomputing variant stages the `W` tile, evaluates `basis_terms_for<Kind>` on the layer input
  `activation[j]` into a third plane (values) and the derivative plane, and reduces in the same
  order as before. The guard is `CheckedEarlier`: the forward already checked these values.

Unchanged: the FP64 executor (its basis kernels are FP64-ALU bound and unstaged, so it keeps
the stored rows; bitwise C2/C9), trainable RBF layers (their nonlinear reductions read `Phi'`
and the log-width rows), rows longer than the staged tile (above 85 terms: stored rows), the
cuBLAS contractions, the parameter part of the finish kernel.

Because the recomputation evaluates the same formula on the same FP32 input, the recomputed
rows are the stored rows, and the results are bitwise unchanged in both builds (below). The
contract change (which layers keep `Phi'`, one region less) is in
[CONTRACT.md, contraction engine](../../CONTRACT.md).

Memory: one `capacity*inputs*terms` FP32 region less per fixed-basis layer, e.g. 58.7 MB per
256-wide Chebyshev(7) layer at capacity 8192, 117 MB per 1024-wide layer at capacity 4096.

## Profiling (AGENTS.md rule 6)

nsys kernel summaries, FP32 matched step N=1, graph nodes traced
([nsys/](C3-bench/nsys/), per step):

| Kernel, 256-wide | pre-C3 | C3 |
|---|---:|---:|
| `basis_kernel<Chebyshev, float>` (3 layers) | 3 x 154.7 us (15.3%) | 3 x 83.7 us (9.0%) |
| `backward_finish_kernel<float>` | 3 x 103.0 us (10.2%) | 3 x 89.2 us (9.6%) |
| SGEMMs (forward tn, coefficient nt, input nn) | 2.20 ms | 2.21 ms |
| GPU time per step | 3.201 ms | 2.957 ms |

At 1024-wide: `basis_kernel` 2 x 308 -> 2 x 177 us, finish 2 x 192 -> 2 x 184 us, GPU time
15.44 -> 15.10 ms (SGEMMs 91%). The basis kernel now writes one tensor instead of two (59 MB at
256-wide, about 0.85 TB/s, at the DRAM limit). The finish kernel reads `W` and the input instead
of `W` and `Phi'`; its time is the `W` read plus the evaluation.

**What remains.** At 256-wide, `basis_kernel` + finish + bias are about 0.6 ms of 2.96 ms; at
1024-wide about 0.8 ms of 15.1 ms. The rest is cuBLAS SGEMM at 18-24 TFLOPS. Removing the
remaining `Phi` and `W` round trips needs fused GEMMs (stage 2).

## Stage 2: fusion prototypes (not adopted)

Standalone prototypes against cuBLAS 13.1 on the RTX 3090, FP32, Chebyshev K=7
([prototypes/](C3-bench/prototypes/), [results.txt](C3-bench/prototypes/results.txt)).

**GEMM core.** A hand-written SIMT SGEMM (128x128 tile, 8x8 per thread, register-staged
double buffer) on the forward shapes reaches 14.2-16.2 TFLOPS without split-K and
17.7-19.3 TFLOPS with a 4-7-way split-K (main kernel only, partials not reduced), against
cuBLAS 18.7-19.5. cuBLAS itself runs the 1024-wide forward as `ampere_sgemm_128x128_tn` with a
7-way split-K (1,792 blocks): the 256-block grid of a plain tiling leaves a 1.56-wave tail.

**Fused forward** (`Y = Phi(X)*C^T + b`, basis evaluated into the A tile in 16-column windows,
split-K partials summed by a reduction): 0.63-0.65 ms at 256-wide (library pre-C3: basis 0.155 +
SGEMM 0.42 + bias 0.015 = 0.59 ms; C3: 0.52 ms) and 4.32-4.98 ms at 1024-wide (library:
about 3.3 ms). Nsight Compute: 27% of the issued instructions are not FMAs. Evaluating the basis
(with its derivatives, as the shared formulas produce both) for every column tile costs about a
quarter of the issue slots. That is more than the unfused basis kernel's memory time, which is
only about 10% of the 1024-wide GEMM.

**Fused input VJP** (`W = U*C` over outputs, 256x128 tile with 16x8 per thread, 4-stage
`cp.async` pipeline, column tiles of whole inputs; epilogue stages `W` in 64-row passes and
reduces each (sample, input) against recomputed `Phi'`). Against the library path (cuBLAS `W` +
recompute finish): 1.27x slower at 256-wide, 1.34x at 1024-wide, 1.33-1.73x on small layers,
0.93x on the 256->10 layer. Its main loop alone reaches 16.3 / 17.5 TFLOPS against cuBLAS's
`cutlass_80_simt_sgemm_256x128_8x4_nn` at 20-24. Nsight Compute: issue rate 0.71 per scheduler
against 0.86 for the CUTLASS kernel, 21% non-FMA instructions in the main loop body against 12%.
The epilogue adds 150-170 us: at one block per SM (209 registers) the derivative recurrences,
which round-trip through shared memory, are latency bound.

The fused kernels compute the same values (the input VJP bitwise, since both are in-order FMA
chains over the outputs), so correctness was never the obstacle; speed is. Matching the
CUTLASS kernels (warp-tiled fragments, multistage pipelines, split-K/stream-K) is library-scale
work. Without that, fusion loses more in the GEMM than it saves in memory traffic on every shape
except the narrow 256->10 layer, which is worth about 12 us per step.
