# R4: source layout by execution properties

Backlog item R4 (P1), stage B, pass 7 (R4 → R5 → C5). Date: 2026-10-13, branch
`cpp-foundation`, base `6e54fbd` (aarch64/GB10 port). Machine and commands as in
[port-aarch64.md](../port-aarch64.md): Linux aarch64, GB10 (sm_121), CUDA 13.0, GCC 13.3,
Release builds `build-cpu` (CPU-only + Python), `build-cuda` (parity, `KAN_CUDA_FMA=OFF`,
Python, benchmarks) and `build-cuda-fma` (performance build).

R4 is a pure reorganization of `src/`. Public headers in `include/kan/` did not move, so
the installed package, include paths and API are unchanged (no contract change). No
symbol was renamed; every private symbol stays in `kan::detail`.

## Design

The backlog asks for grouping by properties that matter for execution rather than by
mathematical lineage ("orthogonal/harmonic"; Fourier is also orthogonal, B-splines are
not). The grouping that follows from the code:

| Directory | Contents | Execution property |
|---|---|---|
| `src/core/` | `layer.cpp` (carrier-independent Layer protocol, SiLU residual branch), `network.cpp`, `input_map.cpp`, `checks.hpp` (shape/finiteness errors), `host_device.hpp` (`KAN_HOST_DEVICE`, portable math), `residual_formulas.hpp`, `input_map_formulas.hpp` | independent of the carrier |
| `src/carriers/` | `basis_types.hpp` (`BasisKind`, `BasisViewOf`, `BasisRowOf`), `basis_formulas.hpp` (compile-time `basis_terms_for` and runtime `visit_basis_family` dispatch), `basis_view.hpp` (config → view bridge, also used by `resident.cu`), `basis.cpp` (validation, `evaluate_basis`) | family dispatch shared by both backends |
| `src/carriers/polynomial/` | `polynomial_formulas.hpp`: Chebyshev, Legendre, Jacobi, Hermite | global support; every term every input; one three-term recurrence; grows outside [-1,1] |
| `src/carriers/trigonometric/` | `fourier_formulas.hpp` | global, periodic; one sin/cos pair per harmonic |
| `src/carriers/local/` | `local_formulas.hpp`: Cox–de Boor B-splines (`max_spline_degree`, span search, fixed scratch), Gaussian RBF, Mexican hat; `local_operations.cpp`: `insert_knot`, `adapt_grid`, `set_rbf_parameters` | compact support (B-spline: degree+1 nonzero terms) or decaying tails; data-dependent grids/centers |
| `src/carriers/rational/` | `rational.cpp`, `rational_internal.hpp`, `rational_formulas.hpp`, `rational_operations.cpp` (`set_rational_parameters`) | nonlinear in parameters; per-edge P/Q; denominator policies |
| `src/backends/cpu/` | `edge_ops.hpp`, `linear_engine.hpp` (expansion + contraction), `basis_edges.cpp`, `rational_edges.cpp`, `basis_host.hpp` (throwing CPU guard) | CPU execution |
| `src/backends/cuda/` | `resident.cu`, `cuda_runtime.cpp`, `cuda.cu` (deprecated adapter) | optional `kan::cuda` target |
| `src/init/` | `initializers.cpp`, `moments.cpp/.hpp`, `portable_math.hpp` | initializers (cross-carrier feature, kept together) |

Decisions:

- **Formula split.** `src/detail/basis_formulas.hpp` was split along the family groups;
  each group header is self-contained (includes what it uses: `core/host_device.hpp`, and
  `carriers/basis_types.hpp` where it uses the family tag or views; all 21 private headers
  compile standalone), and `carriers/basis_formulas.hpp` includes all three and keeps
  the dispatch. Function bodies were moved verbatim. C5 (sparse B-spline storage) then
  touches `carriers/local/`, the CPU linear engine and the CUDA basis kernel; polynomial
  and Fourier code is not in its diff.
- **Family operations.** `families.cpp` was split: local-family operations to
  `carriers/local/local_operations.cpp` (the `git mv` target, 83% similar),
  `set_rational_parameters` verbatim to `carriers/rational/rational_operations.cpp`.
- **Input maps and init.** Input maps are a network element kind independent of the
  carrier, so they are in `core/`. Initializers depend on every family (reference moments)
  and on the Layer/Network API; they stay a separate top-level `src/init/` rather than being
  scattered over the carrier groups.
- **CPU backend.** The carrier loops (`edge_ops.hpp`, `basis_edges.cpp`, `rational_edges.cpp`)
  and the linear engine were in `src/carriers/`; they are CPU execution, so they moved to
  `backends/cpu/`. `basis_host.hpp` holds the CPU's throwing guard and is CPU-only.
- **Dependency direction.** `core/layer.cpp` includes `backends/cpu/edge_ops.hpp` (the CPU
  Layer dispatches to the CPU carrier loops) and `carriers/basis.cpp` includes
  `backends/cpu/basis_host.hpp` (`evaluate_basis` uses the CPU's throwing guard). Both are
  CPU-host code in the `kan` target; `backends/cuda/` depends only on `carriers/` and `core/`
  formulas. Recorded in CONTRACT rather than moved, to keep R4 a pure move.
- **Includes.** `kan` and `kan_cuda` get `src/` as a PRIVATE include directory and every
  private include is written relative to `src/` (`"core/checks.hpp"`,
  `"carriers/rational/rational_formulas.hpp"`) instead of `../`. PRIVATE: not part of the
  exported targets' interface; the installed include tree is still only `include/`.
  `residual_formula_test` already compiled with `-I src`; its include changed from
  `detail/residual_formulas.hpp` to `core/residual_formulas.hpp` (a compile dependency, not
  an R5 rename).
- **`quantum/`.** No empty directory (git does not track one and a README would only repeat
  the plan). The planned location of M5 carriers is recorded in
  [CONTRACT.md](../../CONTRACT.md#extension-boundaries) and the README: carrier math under
  `src/carriers/quantum/`, a simulator adapter that needs its own execution engine under
  `src/backends/`.
- **`resident.cu`: moved, not split** (recorded follow-up). The file is one translation
  unit of 2628 lines with 126 SASS functions (kernel instantiations); its compile takes 19.1 s in the parity
  build on this machine (`make .../resident.cu.o` after `touch`, 20 cores idle), while the
  whole parity build is 21.9 s with `-j20`. A split into several `.cu` files (e.g. basis,
  rational, input map/residual, contraction, training graph) would let nvcc run in parallel,
  but the kernels and plans share TU-local device helpers and anonymous-namespace types;
  splitting needs a private header for the plan types, explicit template instantiations per
  scalar, and either `-rdc` (device link step; changes code generation and can block
  inlining across files) or duplicated inline device helpers. That is not a cheap, provably
  neutral move, so R4 only moves the file. Follow-up: split along the plan boundaries when
  compile time becomes a bottleneck, with a SASS comparison as below.

## After-state

### Generated code

[objdiff.py](R4-bench/objdiff.py) compares the two builds function by function (host code
by `objdump -dr`, device code by `cuobjdump -sass`), normalizing addresses and the per-file
hash nvcc puts into anonymous-namespace names (it is derived from the source path). Result
([codegen.txt](R4-bench/codegen.txt)):

| Build | Host `libkan.a` | Host `libkan_cuda.a` | `resident.cu` SASS |
|---|---|---|---|
| CPU-only | 114/115 identical | — | — |
| parity | 114/115 identical | 370/370 identical | identical (817457 lines) |
| FMA | 114/115 identical | 370/370 identical | identical (797569 lines) |

The one difference is `kan::set_rational_parameters`, now alone in its translation unit:
GCC inlines the destructor of the temporary `std::variant` carrier, which in
`families.cpp` was a call to a TU-local `.isra` clone shared with the other operations.
No arithmetic is involved (validation, copies, `set_carrier`); the function's tests
(`carrier`, `m4_layer`, `rational_policy`, Python) pass. Every kernel and every other host
function is instruction-identical (`.text`; data sections are not compared, but every
constant-bearing body moved verbatim, which the review checked paragraph by paragraph), so
the move cannot change results on any input, not only on the golden samples.

[csv](R4-bench/c9-f32-matched-step.csv)) against the port baseline
(`port-aarch64/bench/c9-step.csv`), ms per step, median of windows:

| Case | Port baseline | R4 |
|---|---|---|
| 64x64x32x16, B=1024 | 0.1427 | 0.1309 |
| 16x24x8, B=1024 | 0.0643 | 0.0598 |
| 256x256x256x10, B=8192 | 5.2972 | 5.3135 |
| 1024x1024x1024, B=4096 | 23.8748 | 23.5578 |

Checksums are identical; differences are run-to-run noise.

## What R5 will need

R5 renames tests and benchmarks by feature, mirroring `carriers/`. References that must
move with the names:

- `CMakeLists.txt`: the CPU `foreach(suite ...)` list, every individual `add_executable` /
  `add_test` for CUDA and Python suites, test-specific properties (`initializer_training`,
  `residual_training` timeouts; `residual_formula_test` private include), the manual
  `m3_large_basis_test`, the `cuda_deprecation_*` probes, and the `m2/m3/m4_benchmark` targets.
- `scripts/sanitizers.sh`: hard-coded executable lists (`memcheck_tests`, `deep_tests`) and
  the `resident_fused_expansion_test` initcheck exception.
- `scripts/bench_baseline.sh` (`${suite}_benchmark` for m2/m3/m4, output `frozen-$suite.csv`),
  `scripts/benchmark-m2.ps1` (`m2_benchmark.exe` default), and the frozen benchmark names in
  evidence comparisons (`compare_bench.py`, port baselines `frozen-m{2,3,4}.csv`).
- `tests/support/*.hpp` paths used by `docs/evidence/port-aarch64/tf32/tf32_diag.cpp`.
- Test names quoted in CONTRACT.md, README and `docs/BACKLOG.md` (R5 row, journal); CI
  (`.github/workflows/cpu.yml`) runs whole CTest suites and names no tests.
- Frozen benchmark case labels printed into the CSVs (`m3_resident_full`, `m3_transfer_full`
  in `benchmarks/m3_benchmark.cpp`, `m4_resident_full`, `m4_transfer_full` in
  `benchmarks/m4_benchmark.cpp`) are baseline keys: keep them, or map them explicitly.
- Evidence helpers naming the benchmarks: `docs/evidence/backlog/rational_policy_profile.cpp`
  (m4_benchmark fixture), `docs/evidence/m4/summarize_matched.py`.
- The frozen benchmarks are a measurement contract ("no regression on frozen benchmarks");
  renaming them should keep their cases and output format unchanged so baselines stay
  comparable.
