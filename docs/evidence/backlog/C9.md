# C9: graph-captured training steps, deferred status, on-device loss

Backlog item C9 (P1), stage B. Date: 2026-10-06, branch `cpp-foundation`. Baseline: `ba60bf5`
(`build-b-c9base`, parity build). Final: C9 commits rebased on the M4 merge `b92cc5c`
(`build-b-c9`, parity build; `build-b-c9-fma`, performance build). This item extends the public
resident API and changes the resident synchronization contract; that is recorded here, as
`AGENTS.md` rule 5 requires.

## Scope and the extension beyond C9

C9 as written: check the device status once per step or once per N steps instead of the three
memcpy + synchronizations per step after `forward`, `backward` and `sgd`, and capture the step in
a CUDA Graph. The owner's priority for this pass was that a *real* training loop must not be
slower than PyTorch. The C1 evidence showed why the resident API could not deliver that: the
upstream gradient of the caller's loss had to come from the host every step (9.5 ms of the
27.8 ms 1024-wide FP32 step). The scope was therefore extended, minimally, by:

1. **On-device loss**: `Loss::MeanSquaredError` against a resident target (`upload_target`), with
   `download_loss()`. MSE is the only loss; others would follow the same path (a kernel writing
   `upstream.back()` and a loss scalar).
2. **Staged batches**: `train_step(input, target, batch, rate, l2)`, double-buffered page-locked
   host slots and device regions, a copy stream, and events, so a new host batch every step
   overlaps the previous step's compute.

No existing signature changed. Eager calls keep their synchronous semantics: each still checks
and reports its own status. The FP64 default path is unchanged (golden dumps byte-identical,
below). The API is described in `include/kan/resident.hpp` and the contract in
[CONTRACT.md, "Training steps (backlog C9)"](../../CONTRACT.md).

### API decision

| Call | Purpose |
|---|---|
| `train_step(rate, l2 = 0, loss = Loss::OutputGradient)` | one step on the resident input; upstream = the uploaded one (bitwise the eager sequence) or the device MSE gradient |
| `train_step(input, target, batch, rate, l2 = 0)` | one MSE step on a new host batch, staged asynchronously |
| `upload_target(target)` | resident MSE target (like `upload_output_gradient`) |
| `download_loss()` | MSE of the last step's forward pass |
| `set_status_interval(n)` / `status_interval()` | deferred status policy (default 1) |
| `check_status()` | explicit check |
| `trained_steps()` | committed steps as of the last check |

Python: `kan.Loss`, the same methods, the `status_interval` property and `trained_steps`.

Alternatives considered and rejected:

- *Making `forward`/`backward`/`sgd` asynchronous*: this would silently change the error semantics
  of the existing API. The fast path is a new call.
- *A per-step `stage_batch` + `train_step` pair*: the single call `train_step(input, target, ...)`
  gives the same overlap. The host returns as soon as the batch is converted and the step is
  enqueued, so the next call's conversion and copy run while the GPU computes. It has no
  "pending batch" state to specify.
- *Commit by copying candidates into parameters* (no region swap): this costs 2x the parameter
  bytes per step. The executor keeps its two parameter regions and swaps them every step. A
  device commit kernel turns the swap into a rollback on failure.
- *Learning rate in device memory*: a value written per step would race with queued replays.
  Instead the instantiated candidate node's parameter is updated (`cudaGraphExecKernelNodeSetParams`
  affects only later launches), so a schedule needs no re-capture.

## Deferred status: semantics

- Status words: a step writes its forward (and loss), backward and SGD-candidate results into
  three sticky device words. Eager calls use word 0 and leave it clear.
- `commit_kernel`, the last node of a step: if all words are clear it increments the device
  committed-step counter. Otherwise, for the first failing step since the last check, it records
  the bits of the first failing phase (forward before backward before SGD, i.e. the exception the
  eager calls would have raised). It also copies the current parameters over the candidates, so
  the region that becomes active after the host's swap holds the last good parameters. The words
  stay set, so every later step of the interval rolls back too.
- The check (every `status_interval()` steps, `check_status()`, and the start of every other
  non-const call) reads the 32-byte control block in one copy. It raises `std::overflow_error` or
  `std::domain_error` with the eager message plus the step's index since construction and the
  number of later steps that committed nothing. For example: `nonfinite resident numerical result
  in training step 2 (deferred status check; that step and the 1 later steps of the interval
  committed no update)`. It then clears the words.
- Afterwards: parameters of the last good step, `trained_steps()` = failing step index, stale
  outputs/gradients/loss, the last batch is still the input/target, and the executor is usable.
- Attribution was tested on these cases: an overflow at step 2 reported by the check after step 3;
  the first failure winning (a pole at step 1 over a loss overflow at step 2); interval 1 reporting
  at the failing call; seven synchronous calls each reporting a pending failure once; SGD
  width-validation failure of a trainable RBF; the state afterwards bitwise equal to a reference
  that ran only the good steps; and continued training.
- The destructor cannot throw, so a failure pending at destruction is lost. This is documented:
  call `check_status()` first.

Why the phase words exist: the first implementation used one sticky word. A guarded-rational pole
in forward zeroes that edge's caches, and backward then divides by them, so the step reported
`overflow_error` where the eager sequence reports `domain_error`. The per-phase words restore the
eager attribution (`first_failure_of_an_interval_wins`).

## Matched benchmark against PyTorch

**Protocol.** [train_bench.cpp](C9-bench/train_bench.cpp) and [torch_bench.py](C9-bench/torch_bench.py)
run the same four review topologies with Chebyshev K=7 and the same work per step. The model is
`torch_reference.py`'s: per layer `cheb(h).flatten(1) @ C.T + b`, coefficients `N(0,1)*0.1/sqrt(I*K)`,
zero bias, manual SGD at rate 1e-3.

- **matched**: `x` and the upstream are resident; a step is forward + backward(upstream) + SGD,
  exactly `torch_reference.py`.
- **realistic**: every step trains on a new (input, target) batch taken from a host dataset of 4
  distinct batches, cycled. The step is forward + MSE + backward + SGD, and the loss is never read
  back. PyTorch follows its best practice: page-locked float tensors copied with
  `non_blocking=True` (the graph variant copies into static buffers before `replay()`). KAN gets
  `double` host arrays (its API type) through `train_step(input, target, ...)`.

Implementations:

- KAN *pre-C9 eager*: the `ba60bf5` build, with `forward(); backward(); sgd()` (realistic:
  `upload_input`, `download_output`, host MSE gradient, `upload_output_gradient`).
- KAN *step N=1* and *N=64*: `train_step` at status interval 1 (the default) and 64.
- PyTorch 2.14.0+cu130: *eager*; *CUDA graph*, the whole step captured once with
  `torch.cuda.graph` (warm-up on a side stream); *torch.compile*. The default inductor backend
  fails here (`TritonMissing`: Triton is not available for this Windows Python 3.13 venv), so
  the `cudagraphs` backend is used: AOTAutograd forward/backward as CUDA-graph trees with an eager
  SGD.

TF32: KAN `Precision::TensorFloat32`, PyTorch `allow_tf32 = True`.

[run_bench.sh](C9-bench/run_bench.sh) interleaves ABBA: repetition r runs KAN first when r is odd
and PyTorch first when r is even. Each process measures 3 timing windows (200 steps for the small
nets, 50 FP32 / 10 FP64 at 256-wide, 20 FP32 / 2 FP64 at 1024-wide, after warm-up), and there are
3 repetitions, so each cell has n = 9 windows. Cells show the median of ms per step and
[min-max]; ratios use the best KAN median.

**GPU conditions.** RTX 3090, driver 591.86, WDDM, desktop compositor active, 15:37-15:53.
Before the run an unrelated external CUDA job (`Python31310\python.exe`, another project's
training) used the GPU at 120-230 W. Measurements started only after it ended. A monitor sampled
`nvidia-smi` every 30 s during the run (32 samples): no other compute process
([gpu-monitor.txt](C9-bench/final/gpu-monitor.txt), [gpu-before.txt](C9-bench/final/gpu-before.txt),

**The target is met.** The FP32 step is faster than PyTorch eager on every topology in both
protocols, already at the default status interval 1. It is also faster than PyTorch with a
whole-step CUDA graph and with `torch.compile`: 0.29x-0.71x of the best PyTorch time with
N=64, and 0.38x-0.74x at N=1 (worst cell: 64-wide realistic, 0.383 vs 0.515 ms for the CUDA
graph). `torch.compile`
(cudagraphs backend) is slower than eager at 1024-wide on this machine (high variance,

baseline could not be measured. At 1024-wide a fused Triton step could close part of the gap,

(91% SGEMM, below) is where it could gain least.

the staged copy of the next batch is fully hidden behind compute. At N=1 the input conversion
and copy of each batch (about 2 + 5 ms, PCIe at about 3.2 GB/s on this machine) cannot overlap,
because the step waits for its own status; the target copy still overlaps the forward pass.

**Findings and fixes:**

1. *Host conversion serialized with the copy (fixed, `57eda18`).* The nsys GPU trace of the
   realistic 1024-wide FP32 step at N=1 (first implementation, 36.8 ms;
   [nsys-realistic-1024-before-fix.txt](C9-bench/nsys-realistic-1024-before-fix.txt)) showed the GPU idle for
   9.5 ms while one host thread converted and validated the 8M doubles, then two serial 5.1 ms
   copies, then 15.8 ms of compute. A microbenchmark of variants
   (pageable/pinned destination, branch-free clamp, 2-8 threads) found the single-thread loop
   memory bound at about 1 GB/s of doubles, and 8 threads at 2.9-3.5 ms. Fix: a branch-free
   conversion split over up to 8 threads for batches above 2^18 values. The input copy now
   starts while the target converts, and the step waits for the target inside the graph (an
   event-wait node before the loss), so the target copy overlaps the forward pass.
   Result: 36.8 -> 24.1 ms (22.7 ms in the final run).
2. *Network-input gradient (fixed, `8568119`).* At 1024-wide the step's 6 SGEMMs were 91% of
   GPU time. One of them (`W = U*C` of layer 0), together with its `backward_finish` reduction,
   only produces the gradient with respect to the network input. That gradient cannot be
   observed after a training step, and PyTorch does not compute it either (`x` does not require
   grad). The step now skips it, which is why FP64 moved from slower than PyTorch to faster
   (677 -> 567 ms at 1024-wide).
3. *Sanitizer noise in the graph code (fixed, `7c54280`).* memcheck reported 302 API errors: the
   SGD-node lookup called `cudaGraphKernelNodeGetParams` on cuBLAS library kernel nodes, which
   return `cudaErrorInvalidDeviceFunction` (tolerated and cleared, but they could hide real errors).
   The node now comes from `cudaStreamGetCaptureInfo` right after the candidate launch: 0 errors.
4. *Per-phase status words.* A correctness fix, not performance; see the deferred-status
   section above.

**Nsight Compute on the top kernels** (1024-wide FP32 step inside the graph,
`--graph-profiling node`, SpeedOfLight; ncu fixes clocks, so durations are above the nsys ones;
profiled before `8568119`, whose kernels are the same minus one GEMM and one finish;
[ncu-1024-f32.csv](C9-bench/ncu-1024-f32.csv), [summary](C9-bench/ncu-1024-f32-summary.txt)):

|---|---:|---:|---:|
| `ampere_sgemm_128x128_tn` (forward, cuBLAS) | 3.31 ms | 72% | 16% |
| `basis_kernel<Chebyshev, float>` | 0.31 ms | 51% | 88% |
| `backward_finish_kernel<float>` | 0.33 ms | 33% | 93% |

The non-GEMM kernels run at 83-93% of DRAM bandwidth: they are memory bound at their tensor
sizes and need no further local tuning. What remains is (a) the cuBLAS SGEMMs (cuBLAS's choice of
SIMT kernels, about 72% of SM throughput; TF32 tensor cores make the 1024-wide step 1.5x
faster), and (b) the `Phi`/`Phi'` round trips through global memory (about 4 B*I*K*4 bytes per
layer and step), which **C3 (fused expansion)** would remove. By the profile, C3 would save the
`basis_kernel` launches (2 x 0.31 ms) and the remaining `backward_finish_kernel` (0.33 ms), about
1 ms of the 15.6 ms 1024-wide step (6%). At 256-wide, where the C1 profile put these kernels at
about a quarter of the step, it would save roughly 0.6-0.8 ms of 3.3 ms, if the expansion were
fused into the GEMM operand loads.

## Remaining gaps

None in FP32 or TF32: every topology and protocol is faster than PyTorch eager, CUDA-graph and
`torch.compile` (cudagraphs). FP64 realistic at N=1 ties PyTorch eager at 256- and 1024-wide
(within the run-to-run spread, above). Its root cause is the FP64 DGEMM rate shared by both
libraries plus the non-overlapped input copy at N=1, and N >= 2 removes the latter. The next
large-step gains are C3 (fused expansion, estimate above) and, for these GEMM-bound steps, TF32
where its tolerance is acceptable.

## Deviations from the brief

1. **Default status interval 1.** The brief allowed "once per step, or once per N steps". The
   default is one check per step, so each failure is reported by its own call, the least
   surprising contract for existing users. N is an explicit setting, and the FP32 target is met at
   N=1 in both protocols; N=64 is faster still. Whether training code in this project should
   default to a larger N is a policy choice for the owner (open question below).
2. **`train_step` does not compute the network-input gradient.** The eager `backward()` still
   does. The parameter updates are bitwise those of the eager sequence, but a nonfinite gradient
   with respect to the network input no longer fails a training step. This matches PyTorch, and
   the brief requires the same work per step as `torch_reference.py`, which skips it. It is
   documented in CONTRACT.md.
3. **Eager calls stay synchronous** (each still checks its own status) instead of all becoming
   deferred. Changing their error semantics was not needed for the target and would have changed
   an existing contract.
4. **`torch.compile` with inductor could not be measured**: Triton is unavailable in the
   project's Windows venv. The `cudagraphs` backend and a manual whole-step `torch.cuda.graph`
   capture are reported instead. The latter is the stronger PyTorch baseline here.
5. **Host threads in the staging path.** Up to 8 short-lived `std::thread`s convert large
   staged batches. This was not in the brief, but the profile showed single-thread conversion
   would serialize with the PCIe copy. Small batches (below 2^18 values) convert on the calling
   thread.
6. **Only MSE** as an on-device loss (the brief: "at least MSE"). Other losses can follow the
   same kernel slot.
