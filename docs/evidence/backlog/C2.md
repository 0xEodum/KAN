# C2: resident contraction engine on GEMM

Backlog item C2 (P0), stage B. Date: 2026-10-02, branch `cpp-foundation`.
Baseline: `22bd70e` (C2 regression suite, naive kernels; built as `build-b-c2base`).
This changes the resident numerical contract (no CPU/GPU bit identity) and adds a
build dependency (cuBLAS, CUDA 12+). Both are recorded here as `AGENTS.md` rule 5
requires and were approved by the repository owner before the work started
("we cannot preserve bit-identity; we will treat this as an acceptable deviation";
cuBLAS dependency: "Yes, no problem").

## Change

For `BasisEdges` and `TrainableRbfEdges` a KAN layer is the expansion
`Phi: R^I -> R^(I*K)` and a dense contraction. Before C2 the resident executor ran the
contraction and its VJPs as three hand-written kernels with one thread per result
element, no tiling and uncoalesced coefficient reads (`forward_kernel`, `input_kernel`,
`parameter_kernel`), and the trainable-RBF center/log-width reduction walked
`batch*inputs*outputs*K` products. Row-major tensors: `Phi`, `Phi'` (batch, I*K);
`C` (O, I*K); `U = dL/dY` (batch, O).

| Product | Before | After (`src/resident.cu`, `expansion_forward/backward`) |
|---|---|---|
| `Y = Phi C^T + b` | `forward_kernel` | `forward_dot_kernel` (<= 2^23 multiply-adds) or `cublasDgemm_64(T,N)` + `bias_kernel` |
| `dC = U^T Phi + lambda C`, `db = U^T 1` | `parameter_kernel` | `parameter_partial_kernel` + tile sum in `backward_finish_kernel` (<= 2^15 coefficients+outputs) or `cublasDgemm_64(N,T, beta=lambda)` + `cublasDgemv_64` |
| `dx = sum_k Phi' (.) (U C)` | `input_kernel` | `W = U C` by `cublasDgemm_64(N,N)` into shared scratch, reduced in `backward_finish_kernel` |
| RBF center/log-width VJPs | `nonlinear_partial_kernel` over `B*I*O*K` | same kernel over `W`: `B*I*K` |

Every nonfinite result is still reported through the status word: outputs by the
forward kernels, `[dC | db]` and `dx` by `backward_finish_kernel`, nonlinear VJPs as before.

### Decisions

- **cuBLAS for large products, two small kernels for the shapes it handles badly.**
  On the RTX 3090 cuBLAS executes a tiny or long-and-narrow DGEMM as one latency-bound
  32x32 tile without split-K: the forward of a 24x32x112 product takes 42 us
  (warp-per-output kernel: 7 us), the coefficient VJP of a 112x24x1024 product took
  331 us (tiled reduction: about 5 us). Manual split-K through strided-batched DGEMM
  helped some shapes and made others 2x slower ([measurements](#small-shape-measurements)),
  so the small paths are plain kernels with fixed thresholds. Both small kernels are
  FP64-ALU bound like cuBLAS on GA102, so at the thresholds both choices cost about the
  same; C1 revisits the forward threshold for FP32, where cuBLAS SGEMM/TF32 dominates.
- **One `W = U*C` scratch for all expansion layers** (largest `capacity*I*K`), and one
  partials region for the small parameter VJPs (largest `checked * tiles`). Layers run in
  order on one stream, so sharing is safe; the trainable-RBF reduction consumes `W` right
  after `expansion_backward` of the same layer.
- **No allocation during execution.** The cuBLAS handle is created at construction on the
  executor's stream; `cublasSetWorkspace` (after `cublasSetStream`, which resets it) gives
  it a 4 MiB workspace inside the arena. Every arena region is now 256-byte aligned.
  `workspace_allocations()` still counts 2 (arena, status).
- **Deterministic reductions.** cuBLAS GEMM/GEMV without atomics, fixed-order lane and
  tile sums in the custom kernels. Results are deterministic for one GPU, driver and
  cuBLAS version, not bitwise equal to the CPU.
- **`beta = 0` never reads stale gradients.** `lambda = 0` uses `beta = 0`; `lambda != 0`
  copies `C` and uses `beta = lambda` (cuBLAS path) or adds `lambda*C` in the tile sum
  (small path). A test runs a `lambda = 0` backward after an overflowed one.
- **Overflow semantics.** FMA inside a contraction can cancel an intermediate overflow
  that the CPU's unfused sequence reports. The contract states that the check covers
  result tensors. All existing overflow and cancellation tests still pass.
- **Kept.** Kernels outside the contraction (basis, rational, input maps), the plan
  structure, parameter layout `[coefficients | bias | nonlinear]` and the public API.

### Dependency and packaging

- `kan_cuda` links `CUDA::cublas` (PRIVATE; exported as `$<LINK_ONLY:...>` for the static
  library) and requires `find_package(CUDAToolkit 12)`, the first toolkit with the
  64-bit cuBLAS API. `KANConfig.cmake` calls `find_dependency(CUDAToolkit 12)`.
- cuBLAS ships only as a DLL on Windows. Python 3.8+ ignores `PATH` for extension
  dependencies, so the CUDA build of `_kan` failed to import ("DLL load failed") until
  CMake wrote `kan/_dll_paths.py` (the toolkit's `bin/x64` and `bin`, also installed)
  and `kan/__init__.py` registered it and `CUDA_PATH` with `os.add_dll_directory`
  before importing `_kan`. A module built here and run on another machine needs a CUDA
  runtime there (or `CUDA_PATH`); the DLLs are not bundled (cuBLASLt alone is hundreds of MB).
- The evidence link scripts (`golden/build_golden.cmd`, `build_profile.cmd`) add `cublas.lib`.

## Tests

`tests/resident_contraction_test.cpp` (committed first in `22bd70e`; it passed 5/5 on the
naive kernels and pins the behaviour the rewrite must keep):

- wide mixed network (Chebyshev 37->23, trainable RBF 23->41, cubic B-spline 41->5,
  Fourier 5->3; `I*K` and `O` not multiples of any tile), batch 129 below capacity 200,
  three forward/backward(L2)/SGD steps against the CPU, trained parameters, unchanged
  allocations;
- `contraction_engine_paths_agree_with_cpu` (added with the small kernels): a 64->80
  layer (35 920 coefficients+outputs, forward 14.3M multiply-adds at batch 400) and an
  80->3 Jacobi layer, at batch 400 (cuBLAS forward and parameter VJP on layer 1, 7 batch
  tiles of 58/52 samples on layer 2) and batch 7 (all small paths);
- repeated backward after one forward; single sample/edge; empty batch with `lambda` 0.25
  and 0 (all four nonlinear and linear gradient tensors); a smaller batch after a larger one;
- nonfinite outputs, coefficient VJPs and input VJPs are reported, and the executor
  recovers (including a `lambda = 0` backward after an overflowed coefficient VJP).

The comparison is per entry: `|a-e| <= 1e-12|e| + 1e-13 max|e|`. The absolute floor
matters for entries that cancel in long reductions: a 400-sample coefficient VJP of
8.1e-4 from terms up to 0.15 differs by 3.4e-15 (23 ulp of the scale).

All earlier suites pass unchanged, with their original tolerances.

## Benchmarks

**Large steps** ([large_step.cpp](C2-bench/large_step.cpp), forward + upload + backward + SGD,
median of 7 (2 for 1024-wide), two alternating rounds; Chebyshev K=7 unless noted):

| Topology, batch | Baseline | C2 | Speedup |
|---|---:|---:|---:|
| 64->64->32->16, 1024 | 2.12-2.33 ms | 1.16-1.19 ms | 1.9x |
| 256->256->256->10, 8192 | 284-287 ms | 95.4-96.1 ms | 3.0x |
| 1024->1024->1024, 4096 | 6.74-6.86 s | 0.688-0.692 s | 9.8x |
| trainable RBF 256->256->256->10, 8192 | 920 ms | 113 ms | 8.1x |

For comparison, the review measured PyTorch FP64 at 3.11 / 87 / 613 ms on the first
three rows. The 1024-wide step performs about 360 GFLOP, so 688 ms is about 94% of the
RTX 3090's FP64 peak; at this size the step is bound by FP64 arithmetic, which C1 addresses.

**Frozen suites** (`m2/m3/m4_benchmark --backend all --warmups 2 --repeats 7`, ABBA, pooled
median ratio C2/base, geometric mean over cases; [summary.txt](C2-bench/summary.txt), raw CSVs in
[C2-bench/](C2-bench/)):

| Suite | CPU | Resident | Transfer | M1 host |
|---|---|---|---|---|
| m2 (polynomial, Fourier, Gaussian) | 0.998 | **0.606** (0.402-1.017) | 0.723 | 1.013 |
| m3 (B-spline, Mexican hat, trainable RBF) | 0.963 | **0.650** (0.422-0.866) | 0.750 | - |
| m4 (rational, code unchanged) | 0.998 | 0.994 (0.915-1.054) | 1.005 | - |

No basis-layer case is slower than the baseline by more than 2% (m2 case 0, 0.259 vs
0.263 ms). The m4 spread is run-to-run noise of untouched kernels under WDDM.

**Profiling (AGENTS.md rule 6)**, Nsight Systems kernel summaries of base and C2
([nsys-kernels.csv](C2-bench/nsys-kernels.csv)):

- 256-wide: the baseline spends 98% in the naive contractions (`input_kernel` 75 ms,
  `forward_kernel` and `parameter_kernel` 29 ms each per launch). C2 spends 88% in three
  cuBLAS DGEMMs of about 13.8 ms each (7.5 GFLOP: about 540 GFLOPS, the FP64 peak); the
  basis kernel (6%) and `backward_finish_kernel` (1.2%) remain.
- Trainable RBF 256-wide: `nonlinear_partial_kernel` 303 ms -> 1.5 ms per launch (66% -> 3.7%).
  The Gaussian basis kernel is now the largest non-GEMM cost (17.5%, 5.9 ms): C3/C1.
- m2 case 1 (16x24x8, batch 1024): `parameter_kernel` 180 us -> `parameter_partial_kernel`
  30 us; forward 37 -> 49 us; the call is 0.65 -> 0.36 ms.
- 64-wide: `parameter_partial_kernel` (126 us for 29M multiply-adds) is FP64 bound and
  1.75x faster than the cuBLAS DGEMM it replaces for this shape (221 us).

### Small-shape measurements

[dot_vs_gemm.cu](C2-bench/dot_vs_gemm.cu) ([output](C2-bench/dot_vs_gemm.txt)): forward
`T,N` DGEMM against the warp-per-output kernel. 24x32x112: 38-42 vs 7 us; 24x1024x112:
40-42 vs 37-43 us; 64x1024x448: 157 vs 164 us; 256x8192x1792: 13.9 vs 13.6 ms. The cuBLAS
math mode (default or pedantic) changes nothing. Manual split-K of the coefficient VJP
(strided-batched DGEMM over S batch chunks + fixed-order sum), us for S = 1/4/8/16/32:
112x24x1024: 42/94/52/30/32; 168x8x1024: 352/94/52/52/54; 1792x10x8192: 812/2547/1900/1903/1766.
No single split factor helps all shapes, hence the dedicated tiled kernel.

## Review

An independent `cpp-reviewer` pass over the cuBLAS change (read-only) found no CRITICAL or
HIGH issues. It verified every transpose, dimension and leading dimension against the
row-major layouts, `beta` semantics, batch 0 and batch < capacity, scratch sharing, stream
ordering, handle lifetime and exception safety, alignment arithmetic and the exported link
interface. Findings:

- **Fixed (MEDIUM):** a single tolerance relative to the whole tensor could hide errors in
  small entries; comparisons are now per entry with a 1e-13 floor (see Tests).
- **Fixed (MEDIUM):** no test ran a `lambda = 0` backward over a stale nonfinite gradient.
- **Fixed (MEDIUM):** the empty-batch test did not exercise `lambda = 0` or compare log widths.
- **Fixed (LOW):** contract wording on allocations (the handle's internal state is created
  once at construction and not counted), the deviation figure now links here, CUDA 12 is
  required at configure time and in the package config, and the README names the cuBLAS DLL.
- **Accepted (LOW):** FMA cancellation of intermediate overflows is documented, not tested;
  the fixed 4 MiB cuBLAS workspace (the large GEMMs already run at FP64 peak); a memcpy +
  scale on the empty-batch L2 path.

A second pass over the small kernels, the merged finish kernel and the Python DLL handling
approved them. It verified the tile and chunk arithmetic (every tile starts below the batch;
all partials are overwritten on each call), partial indexing and sizing against capacity,
launch limits, and that the new test reaches each path. Its LOW notes: threshold boundaries
are crossed on one side only (accepted), the package config version (fixed), and that a
module built here needs a CUDA runtime on the target machine (documented above and in the README).

## Reproduction

```powershell
scripts\build.ps1 -Cuda -AllowUnsupportedCudaCompiler -Python -Benchmarks -Test -BuildDirectory build-b-c2
# baseline: the same at 22bd70e into build-b-c2base; golden_base.txt / _layers.txt and
# large_base.exe from it into %TEMP%\kan-c2, then (Git Bash):
docs/evidence/backlog/C2-bench/run_all.sh build-b-c2base build-b-c2 /c/Users/<user>/AppData/Local/Temp/kan-c2
```

`run_all.sh` runs the sanitizers, golden comparison, ABBA frozen benchmarks
([run_abba.sh](C2-bench/run_abba.sh), [compare_bench.py](compare_bench.py)), the large steps
and the Nsight Systems summaries.
