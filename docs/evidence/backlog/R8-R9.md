# R8 + R9: shared device-query header and resident parameter upload

Backlog items R8 (P1) and R9 (P1), stage B, pass 4, taken together as the owner decided
([decision](R8-R9-decision.md)). Date: 2026-10-05, branch `cpp-foundation`.
Baseline: `6715723` (C1/C10 closed, R8/R9 added), built as `build-base` in a temporary
worktree. Implementation built as `build-b-r8r9` (MSVC 19.50 + CUDA 13.1 + Python, parity
build) and `build-b-r8r9-gcc` (GCC 15, CPU only). Both items extend the public CUDA API; the
contract changes are recorded here, as `AGENTS.md` rule 5 requires, and in
[CONTRACT.md](../../CONTRACT.md). No existing signature changes, no CPU source changes and
no kernel changes.

## R8: `kan/cuda_runtime.hpp`

- New public header `include/kan/cuda_runtime.hpp` declares `bool kan::cuda::available() noexcept`
  (same name, not deprecated). It has no CUDA dependency, so the CPU-only Python build, which
  includes `kan/resident.hpp` for `kan::cuda::Precision`, still compiles; the declaration is
  only called when CUDA is enabled.
- `kan/resident.hpp` and `kan/cuda.hpp` both include it; the declaration was removed from
  `kan/cuda.hpp`. A user of `kan/cuda.hpp` or `kan/resident.hpp` sees no change.
- The definition moved from the legacy adapter `src/cuda.cu` to `src/cuda_runtime.cpp`, a
  host-only C++ source in `kan_cuda` (it needs only `cudaGetDeviceCount`; CMake gives it the
  CUDA runtime include path through the target's private `CUDA::cudart` link). `src/cuda.cu`
  is now only the deprecated adapter.
- `src/resident.cu` and `python/bindings.cpp` no longer include the legacy `kan/cuda.hpp`
  (it was included only for `available()`).
- Installation: `include/` is installed as a whole, so the header is installed and exported
  with the package. The installed consumer (`tests/consumer`) includes it explicitly.

## R9: `ResidentNetwork::upload_parameters(const Network&)`

```cpp
void upload_parameters(const Network& network); // new method; Python: upload_parameters(network)
```

### Semantics

| Aspect | Decision |
|---|---|
| Uploaded state | Every trainable value the executor holds: coefficients of every carrier (rational numerators) and biases, trainable RBF centers and log widths, rational denominators, LayerNorm gain and bias. This is exactly what `download_parameters()` reads back from the device, so the round trip is exact. |
| Structure (rejected on mismatch) | Layer count; per position the kind (KAN layer / input map) and dimensions; carrier or map kind; fixed configuration by `operator==`: whole `BasisConfig` of a `BasisEdges` layer (family, size, Jacobi alpha/beta, Fourier frequency, Gaussian centers and width, B-spline degree and knots, Mexican-hat centers and scales), term count of a trainable RBF, whole `RationalConfig` (degrees, center, scale, epsilon, policy), `AffineMap`, `TanhMap`, LayerNorm epsilon and the presence of gain/bias. |
| Errors | `std::invalid_argument` naming the first differing layer and aspect (`resident parameter upload: layer 6 differs from the executor's network in its fixed configuration`); value errors use the construction messages. Moved-from executor: `std::logic_error`, like every other operation. |
| Guarantee | Strong for every rejection: the structure of every layer is checked first, then every value is validated (FP32: converted) on the host, and only then is anything copied. Parameters, output, gradients, input, upstream and batch are unchanged after a rejection (tested: download, `download_output()` and `backward()` still work and return the old results). A CUDA runtime failure during the copy raises `std::runtime_error` and leaves the parameters unspecified (the output/gradient state is already invalidated at that point). |
| Precision | Same rules and messages as construction: finite; FP32 rejects magnitudes above `FLT_MAX` and trainable RBF widths that are not positive after rounding (`check_basis`, the construction check); values below the FP32 range round. |
| Lifecycle | Success invalidates output and gradients (`has_forward = has_backward = false`): `backward()`, `download_output()`, `download_gradients()` and `sgd()` raise `std::logic_error` until a new `forward()` (and `backward()`). The input, upstream and batch are kept, exactly as after a successful SGD, which also replaces the parameters. Valid at any point after construction, including before any input. |
| Device memory | None allocated; writes the active region of the double-buffered parameter storage (the region SGD swaps in). |
| Python | `ResidentNetwork.upload_parameters(network)`, releasing the GIL; rejections are `ValueError`, lifecycle errors `RuntimeError`. The wrapper's stored topology (used to check gradient snapshots) stays valid because the structure is unchanged. |

### Knots and other configuration: structure, not state

Configuration that can change on the host without changing tensor sizes (B-spline knots moved
through `set_carrier`, fixed Gaussian/Mexican-hat centers and scales, affine maps, rational
center/scale) is treated as structure and rejected, not uploaded. Reasons:

1. **The coefficients are only meaningful with their configuration.** The executor evaluates a
   fixed function space; the coefficients of a different knot vector describe a different
   function. Accepting them would silently combine new coefficients with old knots, and
   uploading the knots too would turn the call into a partial reconstruction.
2. **Refinement changes shapes anyway.** `insert_knot` and `adapt_grid` add a term, so the
   arena layout, the workspaces and the FP32 knot checks (`distinct knots stay distinct`) differ.
   The contract already says to reconstruct the executor after grid refinement; the upload
   enforces it.
3. **One clear invariant.** `upload_parameters(n)` is valid exactly when `n` equals
   `download_parameters()` up to trainable values. Trainable RBF centers/log widths and
   LayerNorm gain/bias are trainable, so only their counts are structure.
4. **No silent snapshot drift.** `download_parameters()` rebuilds the network from the
   construction snapshot plus device values. If configuration were uploadable, the snapshot
   would have to be updated as well, and the plans' converted scalars (FP32 epsilon, scale,
   Jacobi alpha/beta) re-derived.

Fixed affine maps are configuration by the M1 contract ("fixed, not trained"), so they are
also rejected.

### Copies

The parameter region is one dense vector (each plan's block at its offset). Two commit paths,
chosen by profiling (below):

- **Packed** (FP32 always, FP64 up to 1 MiB): a single pass converts and validates every tensor
  into one host buffer covering the region, then one `cudaMemcpyAsync`.
- **Direct** (FP64 regions above 1 MiB): validate every source tensor (finite, read-only pass),
  then copy each nonempty tensor straight from the caller's network: at most four copies per KAN
  layer (coefficients, bias, centers/log widths or denominators) and two per LayerNorm map.

One stream synchronization at the end; the call completes before returning, like every upload.

Nsight Systems, 10 uploads captured between `cudaProfilerStart/Stop` after construction
([profile_upload.sh](R8-R9-bench/profile_upload.sh), [nsys-api.csv](R8-R9-bench/nsys-api.csv),
[nsys-mem.csv](R8-R9-bench/nsys-mem.csv)):

- **No device allocation**: the only CUDA API calls inside the capture are `cudaMemcpyAsync` and
  `cudaStreamSynchronize` (no `cudaMalloc`, `cudaFree` or `cudaMallocHost`); no kernel runs.
- **Copies**: 1 per upload for the small networks and for the large FP32 network, 4 per upload for
  the large FP64 network (direct path: two layers x coefficients + bias); one synchronization each.
- **Link bound for large networks**: the 117 MB FP64 upload is a 36.3 ms copy, the 58.7 MB FP32
  upload an 18.2 ms copy, both 3.2 GB/s, the PCIe rate this machine also reaches with pinned
  memory (C1). The rest of the call is host work: about 9 ms (FP64: structure check and the
  read-only finite pass) and 22 ms (FP32: the conversion pass into a fresh 59 MB buffer).
- **Fixed for FP64 (`8c25ee0`)**: the first version packed FP64 like FP32 into one buffer. nsys
  showed the same 36 ms copy inside a 62 ms call; the remaining 26 ms was writing a fresh 117 MB
  host buffer that FP64 does not need. Copying the validated tensors directly: 62 -> 45 ms. For
  the 0.4 MB network the six direct copies were slower than one packed copy (0.16 -> 0.24 ms), so
  FP64 packs up to 1 MiB (crossover between the two measured sizes; per-copy cost about 15 us).
- **Small networks**: 0.16 ms, of which the copy is 0.12 ms of GPU time and about 17 us of API
  time; construction (stream, arena, cuBLAS handle, per-tensor uploads) costs 2.2 ms.
- **Not done**: FP32 could overlap its conversion with the copy through page-locked chunks, but
  that needs a page-locked staging buffer of its own (the FP32 input staging buffer is sized for
  inputs, not parameters) and still has to validate every value before the first copy. The
  saving would be at most the 22 ms host pass of a 117 MB model, on a call that is not part of
  the training step. Left as an option, not needed for R9.

## Deviations from the brief

- **Copies.** The brief asked for "a bounded number of copies"; FP32 and small FP64 uploads make
  exactly one, large FP64 uploads one per parameter tensor (bounded by the structure, at most four
  per layer), because profiling showed that packing costs 40% of a large FP64 upload.
- **Extra commits.** `3e7f780` repairs the RED log of `48e03fd` (already pushed, so not amended),
  and `8c25ee0` (perf, with its own test case) follows the feature commit, and the installed consumer
  gets its own `test:` commit, so the sequence is test, test, refactor, feat, perf, test, docs,
  docs instead of test, refactor, feat, docs, docs.
- **Documentation fix.** `README.md` and `CONTRACT.md` contained a literal backspace character
  from the C1 documentation (`scripts\build.ps1` written as `scripts<BS>uild.ps1`); fixed while editing.
