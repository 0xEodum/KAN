# Backlog C5: sparse B-spline path

Date: 2026-10-13. Branch `cpp-foundation`, base `d80576a` (R5 closed). Machine: GB10 (sm_121,
48 SMs, 24 MiB L2, unified LPDDR5x), CUDA 13.0, cuBLAS 13.1, CCCL 3.0.1, GCC 13.3
([port evidence](../port-aarch64.md)). Three Python processes of other users held GPU contexts
(15 GB, [gpu-apps.txt](C5-bench/gpu-apps.txt)) and were idle (utilization 0-1% before every
timed run, [gpu-before.txt](C5-bench/gpu-before.txt)).

Finding (BACKLOG C5): only `p+1` of a B-spline's K basis values per (sample, input) are
nonzero, but the CPU and the resident executor stored and multiplied all K, and K grows with
`insert_knot`/`adapt_grid`.

## Result

| | Change | Effect |
|---|---|---|
| CPU | B-spline `BasisEdges` use a sparse engine (`spline_span_terms` + sparse contraction/VJP) | **bitwise identical** (golden `--layers`, CPU checksums), 1.56x (64-wide, K=7) to 16.6x (K=96) faster forward+backward (16-wide b1024 K=7: 1.31x) |
| Resident CUDA | per-layer sparse path (first-term index + p+1 values, gather kernels, sorted coefficient VJP) selected by a device-derived rule | full `train_step` up to 8.75x (FP64), 5.54x (FP32), 4.44x (TF32) faster, arena up to 10x smaller; no measured configuration slower (worst 0.99, within noise); all dense kernels SASS-identical |

## Design

**Shared formula** (`src/carriers/local/local_formulas.hpp`). `spline_evaluate<Dense>` is the
M3 Cox-de Boor evaluation with a compile-time output form: `Dense = true` (`spline_terms`) zero-
fills and writes the K-term rows in place exactly as before; `Dense = false`
(`spline_span_terms`) returns `first = span - degree` (or `terms` outside the domain) and writes
the `degree+1` values/derivatives. Same operations in both forms. (A first version scattered
the sparse result into the dense rows; it changed the dense kernels' SASS and cost the dense
B-spline frozen cases 2-4% (ABBA), so it was replaced; final dense kernels are SASS-identical.)

**CPU** (`src/backends/cpu/linear_engine.hpp`, `basis_edges.cpp`). `SplineExpansion` +
`contract_sparse`/`contract_vjp_sparse` skip the exactly-zero terms and keep the order of the
others. Why this is bitwise: a skipped term is `c*0`, `u*0` or `(u*c)*0` = +-0, and
`s + (+-0) == s` except `-0 + +0`; every sum starts at +0 (zero-initialized gradients) or at
the bias, and a sum is `-0` only if it starts at `-0` and adds only `-0`. So
- an output whose bias is `-0` takes the dense loop (kept signed zero);
- dense `dx` terms are `(u*c)*Phi'`: an overflowing `u*c` at a zero `Phi'` gives NaN, which the
  dense loop propagates and `Layer` reports. `fl(|u|*max_k|c_k|)` overflows iff some
  `fl(|u*c_k|)` does (rounding is monotone), so an edge whose bound overflows takes the dense
  loop for that sample.
Tests pin both cases and a bitwise sweep (degrees 0,1,2,3,5,16, repeated interior knots, a
`+-1e308` domain, 44 interior knots, inputs at knots/endpoints/outside); removing either guard
fails its test ([mutation-cpu.log](C5-bench/mutation-cpu.log)).

**Resident layout** (per sparse layer, arena): `first` (u32 `[inputs][capacity]`, 0 outside the
domain), values and input derivatives (`[inputs][P][capacity]`, samples fastest, zero outside),
the sort's sorted keys/order, a sample-index iota, `2*inputs` segment offsets and the CUB
temporary storage. No dense Phi/Phi' rows, no share of the `W = U*C` scratch or of the small
parameter-VJP tiles. Allocation count unchanged.

**Kernels** (`src/backends/cuda/resident.cu`, "Sparse B-spline path").
- `spline_basis_kernel<P, Residual>`: 32-input tiles; reads X coalesced, writes the rows samples
  fastest through shared memory; with the residual branch also S and silu'.
- `spline_forward_kernel<P>`: lane = sample (256 per block, fewer for layers with few outputs),
  16 outputs per block; C tiles staged with outputs fastest (padded by one vector) and read as
  16-byte vectors. Bias fused unless the residual branch adds `S*W^T` first (then
  `bias_kernel`, as on the dense cuBLAS path).
- `spline_input_kernel<P>`: lane = sample, 8 inputs per block (4, 2 or 1 when the staged rows
  would exceed the shared-memory opt-in limit: on GB10 above 232 terms; the input VJP fits up
  to 1856 terms, the forward up to 1267 (FP32) / 704 (FP64), which bounds the sparse path), output chunks of two vectors: `w_j = sum_o U*C[o,i,g+j]`, `dx = sum_j phi'_j*w_j`.
- Coefficient/bias VJP: CUB `DeviceSegmentedRadixSort::SortPairs` orders each input's samples
  by `first` (CUB documents `DeviceRadixSort` as stable and the segmented sort as sharing its
  implementation; determinism and split independence do not rely on stability); `spline_parameter_kernel<P>`: lane = output (2 per lane), a register window
  of the P coefficients `g..g+P-1`, a coefficient written when the samples pass it; loads of 8
  samples' U rows are issued ahead (the loop was L2-latency bound: 1.3-1.9x); `lambda*C` read only
  for `lambda != 0` (`acc + 0*c == acc`, acc never -0) and streaming dC stores (layer 0 of the
  K=48 256-wide step 5.0 -> 3.7 ms); coefficient ranges split across grid z for layers with few
  outputs and only output-owning warps launched (10-output layer 1.6 -> 1.1-1.5 ms). Every
  coefficient's sum is over the samples with `g` in `[k-P+1, k]` in sorted order for any split:
  deterministic, no floating-point atomics; checksums identical with and without the split.
- P (1..4, degree 0..3) is a template parameter (registers); higher degrees keep the dense rows.

Why these shapes (measured, [device/](C5-bench/device/)): GB10 issues 32-bit shared loads at
16 lanes/clk/SM (1.84 T/s), 16-byte loads at 6.46 T floats/s; the first scalar-load gather
reached 1.1-1.5 TFMA/s (79% of the scalar limit), vectorized 2.6 TFMA/s at small K. L2 reads
2-8 TB/s for <= 16 MiB, DRAM 240-320 GB/s: the coefficient VJP rereads U (capacity*outputs)
once per input, so it is L2-bound while U fits and DRAM-bound beyond (1024-wide layers). ncu
counters are not available to this user (`RmProfilingAdminOnly=1`, no sudo); profiling used
nsys with graph-node tracing (harness linked against shared cudart; the static-cudart link of
the harness crashed and is not used) and microbenchmarks.

Final kernel profile, FP32 256x256x256x10 b8192 K=48 (forced sparse, [nsys](C5-bench/nsys-f32-256-K48-kernels.txt)):
forward 37%, coefficient VJP 35%, basis rows 13%, input VJP 9%, sort 2.4%.

## Selection rule

Per layer at construction (fixed layout for graphs, `upload_parameters`, rollback). Sparse when
degree <= 3; shared memory fits `cudaDevAttrMaxSharedMemoryPerBlockOptin`; `inputs*capacity`
fits 32-bit indices; the dense forward would use cuBLAS at capacity and has at least 2^22
(FP32), 2^23 (TF32), 2^21 (FP64) multiply-adds per SM (`cudaDevAttrMultiProcessorCount`);
`K/(p+1)` >= 2 (FP32), 4 (TF32), 2 (FP64 when `cudaDevAttrSingleToDoublePrecisionPerfRatio` >= 8,
else FP32 values); and >= 6/16/8 when the layer's `capacity*outputs` upstream exceeds half of
`cudaDevAttrL2CacheSize` (FP64's 8 is extrapolated: no FP64 configuration of the sweep exceeds
half the L2). All constants are validated on GB10 only; other devices (in particular full-rate
FP64 ones, which use the FP32 values) are unmeasured. Derivation: forced dense vs forced sparse sweep, then the automatic
choice against dense; the constants are the smallest at which no swept configuration was
slower with the automatic choice (one first rule, ratios 1.5/3 and TF32 floor 2^22, gave
0.90 for FP32 256-wide p3 K6, 0.96 TF32 p1 K6, 0.92 TF32 64-wide K48, so they were raised; the
two configurations whose layout then changed were re-measured).

Crossovers measured (forced paths, step speedup sparse/dense = 1):

| | 64x64x32x16 b1024 | 256x256x256x10 (b8192; FP64 b2048) | 1024x1024x1024 b4096 |
|---|---|---|---|
| FP32 | K/(p+1) 6-12 (work-bound) | < 1.5 (1.05 at 1.5) | 3-6 (U 16 MiB > L2/2) |
| TF32 | 6-12 | 1.5-3 | 12-24 |
| FP64 | 3-6 | 1.5-3 | not measured (dense FP64 1024-wide: s/step) |

Memory (arena, MB): FP32 256-wide K=96 5616 -> 576, 1024-wide K=96 10164 -> 2932; at small K
the sparse layout is slightly larger (index/sort regions; K=6 298 -> 438), one reason the rule
keeps dense there.

## Contract changes (docs/CONTRACT.md)

- New "Sparse B-spline path (backlog C5)" paragraph: layout, kernels, determinism, selection
  rule, memory, precision (TF32: the sparse kernels compute in plain FP32) and one status
  difference: the dense path forms `W = U*C` for all terms, so an overflowing `U*C` at a term with
  zero derivative is reported (`inf*0`); the sparse path does not form it and the step succeeds.
  The CPU keeps the dense behaviour exactly (guard above).
- R2 section: the CPU B-spline sparse engine and its bitwise guarantee.
- Extension boundaries: `spline_span_terms`.
- Dependency: CUB (CCCL 3.0.1, header-only, part of the CUDA toolkit) in `kan_cuda`; no new
  link dependency; CPU-only build unaffected.

## Observations and open questions

- **TF32 dense path accuracy at large K** (pre-existing, reproduced on the base build): in a
  two-layer 64->40->4 network (K=48 and K=30) the dense TF32 input VJP differs from the FP64 CPU
  by 0.46 absolute (expected 0.398, got -0.060) at x=-0.9995: TF32 rounding of `W = U*C` is
  amplified by spline derivatives of order degree/knot spacing. The sparse kernels avoid it
  (FP32). The C5 suite therefore compares TF32 against the CPU only. Owner question: should
  TF32 B-spline layers with large K always take the sparse path (accuracy), or should the C1 TF32
  tolerance note this?
- The sparse coefficient VJP rereads U once per input (L2/DRAM-bound); a CUTLASS-class fused
  formulation or tensor-core densification of sorted chunks could lift the 1024-wide and TF32
  crossovers. Not attempted.
- Degrees above 3 keep the dense rows (compile-time widths 1..4 to bound `resident.cu` compile
  time); more widths are a one-line extension of `with_spline_width`.
- `basis_benchmark --backend resident` stops with "basis result is not finite" in both builds
  (pre-existing; `--backend all` runs fine).

## Independent review

A fresh reviewer agent examined the diff and this evidence (fuzzed the CPU path: 0 bitwise
mismatches in 108,557 cases incl. signed zeros, subnormals, 1e300 magnitudes, degrees 0-4,
repeated knots; probed the CUDA path against the CPU for O in {1,17,65,129}, I in {1,33}, batches
1..263 at capacity 300, 8->2 layers with K=96 for degrees 0-3 with and without the residual
branch, K = p+1, inputs > 65535 and batch > 65535*tile; re-derived the rule against
`final-rule-layers.txt` (0 mismatches) and every table number against its CSV).

| Finding | Resolution |
|---|---|
| HIGH: four automatic-path assertions of the CUDA suite were sized to GB10's 48 SMs (work floor scales with SM count) and would fail on an RTX 3090/4090, A100 or H100 | Kernel tests force the sparse path; the selection and knot-growth assertions use shapes clearing the rule up to ~150-230 SMs and on full-rate FP64 devices (128x64 layers at capacity 4096, ratio-based dense case for knot growth) |
