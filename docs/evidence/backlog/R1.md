# R1: typed per-family basis configuration

Backlog item R1 (P0), stage B. Date: 2026-10-01, branch `cpp-foundation`.
This is a public API and contract change, recorded here as `AGENTS.md` requires.

## Change

The flat `BasisConfig` held every field of every family (`kind`, `size`, `alpha`,
`beta`, `frequency`, `centers`, `width`, `degree`, `knots`, `scales`,
`trainable_rbf`, `log_widths`), with `kind` deciding which fields were meaningful.
It is replaced by:

```cpp
using BasisConfig = std::variant<ChebyshevConfig, LegendreConfig, JacobiConfig, HermiteConfig,
                                 FourierConfig, GaussianRbfConfig, TrainableRbfConfig,
                                 BSplineConfig, MexicanHatConfig>;
```

Decisions:

- **One type per family, holding only that family's fields.** Irrelevant parameters
  can no longer be expressed, so the contract rule "only relevant parameters
  participate" became structural.
- **The term count is derived, not duplicated, for localized families.**
  - Gaussian, trainable RBF and Mexican hat: one term per center.
  - B-spline: `knots.size()-degree-1` terms.
  - This removes the "size must match the vector length" class of errors.
  - `kan::basis_size(config)` replaces `config.size`. It is overloaded per type and
    returns 0 for a spline with too few knots, without unsigned wrap-around.
  - Polynomial and Fourier families keep an explicit `size`.
- **The trainable RBF is its own type, `TrainableRbfConfig`.** It replaces the
  `GaussianRbf + trainable_rbf=true` flag. Its parameters are nonlinear (centers and
  log widths), unlike the linear-in-parameters fixed `GaussianRbfConfig`. This is
  the split R2 builds on.
- **`BasisKind` leaves the public API.** It survives only as
  `kan::detail::BasisKind`, the kernel-dispatch tag in
  `src/detail/basis_formulas.hpp`. `src/detail/basis_view.hpp` converts a typed
  configuration into the flat `BasisView` the shared formulas use.
- **Configurations are values.** `operator==` is defaulted, a value-initialized
  `BasisConfig` is `ChebyshevConfig{4}` (as before), and `Layer(in, out, {})`
  still builds that default layer.
- **`Layer::set_rbf_parameters` checks the length of its vectors.** It now
  requires vectors of the layer's current term count. Before, the stored `size`
  field rejected a different count. Without it, a new center count would silently
  change the term count under unchanged coefficients. The R1 test suite caught this.
- **Python gets one class per configuration type.** Keyword constructors with the
  C++ defaults, a `size` property, value equality and `kan.basis_size`.
  `Layer.basis` returns the typed object. `kan.BasisKind` and `kan.BasisConfig`
  are removed.

- **CPU `Layer` evaluates without revalidating.**
  - `Layer::forward/backward` validate the configuration (`validate_state`) and the
    inputs once per call. They then evaluate through `detail::TrustedBasis`
    (`src/detail/basis_host.hpp`): one view, reused buffers, the same formulas and
    guard.
  - The first R1 build revalidated through two `std::visit` calls and allocated two
    vectors per sample and input. That was +3–6% on CPU-only full calls in the
    frozen benchmarks; this removes it.
  - Public `evaluate_basis` still validates every call.

Not changed: the mathematics, layouts, the resident executor and its device
storage, and the legacy M1 CUDA API (still Chebyshev-only).

Validation messages are unchanged except for splines. "spline knot count must be
size+degree+1" is gone because it can no longer occur. Too few knots now raises
"spline needs at least 2*(degree+1) knots (degree+1 terms)", and an
out-of-range degree raises "spline degree must be in [0,16]".

The default `FourierConfig` has size 3. The old flat default (size 4) was invalid
for Fourier.

## Migration

| Before | After |
|---|---|
| `BasisConfig b; b.size = 3;` | `ChebyshevConfig b{3};` |
| `{BasisKind::Legendre, 5}` | `LegendreConfig{5}` |
| `b.kind = Jacobi; b.alpha = a; b.beta = c;` | `JacobiConfig{size, a, c}` |
| `b.kind = GaussianRbf; b.centers = c; b.width = w;` | `GaussianRbfConfig{c, w}` |
| `... b.trainable_rbf = true; b.log_widths = l;` | `TrainableRbfConfig{c, l}` |
| `b.kind = BSpline; b.degree = p; b.size = n; b.knots = t;` | `BSplineConfig{p, t}` |
| `b.kind = MexicanHat; b.centers = c; b.scales = s;` | `MexicanHatConfig{c, s}` |
| `layer.basis().size` | `kan::basis_size(layer.basis())` |
| `layer.basis().knots` | `std::get<kan::BSplineConfig>(layer.basis()).knots` |

Tests that sweep families with one shared parameter set use the test-only helper
`tests/support/families.hpp` (`test::Family`, `test::basis`), so their parameter
values are unchanged.

Tests whose subject could no longer be expressed were reduced to what remains
meaningful:

- `one_term_bases_and_relevant_parameters_only` → `one_term_bases`;
- `invalid_kind_and_sizes` → `invalid_sizes`;
- the "trainable flag on a wavelet" rejection;
- a spline knot-count mismatch: `{0,0,0,1,1,1}` at degree 2 is now a valid
  3-term basis, and the test asserts that.

## RED

`tests/basis_config_test.cpp` (new, 6 cases) was compiled against the pre-R1 headers
of `e15d547`: 89 compile errors, starting with `'ChebyshevConfig': is not a member
of 'kan'` ([R1-red.log](R1-red.log)).

The project's RED convention (public API plus throwing stubs) does not apply to a
type change: the old and new `BasisConfig` cannot coexist under one name. The
RED is therefore the compile failure, and the RED test is committed together
with the implementation.

## GREEN and equivalence

Build `build-b-r1`: `scripts/build.ps1 -Cuda -AllowUnsupportedCudaCompiler -Python
-Benchmarks -Test` (MSVC 19.50, CUDA 13.1, RTX 3090).

| Check | Result |
|---|---|
| CTest | 20/20 (new `basis_config` suite; Python suites include the new `test_typed_basis_configurations`) |
| GCC 15 CPU-only CTest | 12/12, no warnings |
| Golden dump ([golden/golden.cpp](golden/golden.cpp), ported to the typed API, same fixtures and order) | SHA-256 `64F22EB8…8CD60A3B`, byte-identical to the pre-R3 baseline |

Frozen benchmark checksums (r3 → r1):

- Output and gradient checksums are identical for every case and backend.
- `parameter_checksum` is unchanged everywhere except m3 B-spline, where it drops by
  exactly 28/3 per layer. The old flat config carried the benchmark's shared
  `centers` and `log_widths` even on spline layers, and the checksum summed them:
  Σcᵢ·(i+1) = 28/3 and Σlᵢ·(i+1) = 0. A typed `BSplineConfig` has no such fields.
  For the same reason the Mexican hat checksum keeps its value: only its
  zero-weighted `log_widths` term vanished.

Frozen benchmarks, ABBA order r3, r1, r1, r3 (pooled-median ratio r1/r3, geometric
mean over cases). Raw data is in [R1-bench/](R1-bench/). A script check confirms
that every checksum difference is the B-spline constant above; none is unexplained.

| Suite | CPU | Resident | Transfer | M1 host |
|---|---|---|---|---|
| m2 | 0.744 | 0.967 | 0.929 | 0.990 |
| m3 | 0.771 | 0.912 | 0.979 | — |
| m4 | 1.004 | 0.998 | 1.006 | — |

The CPU speedups (−26% for m2, −23% for m3) come from the trusted Layer
evaluation path. Rational layers (m4) do not use it and are unchanged. The
resident ratios are within WDDM run-to-run noise (single-case outliers in both
directions).

## Review

An independent `cpp-reviewer` pass found no CRITICAL or HIGH issues and verified
three things:

- update atomicity and moved-from behaviour;
- resident upload sizes;
- exact-type pybind11 variant matching.

Its other findings:

- **Fixed:** two placeholders in this document, and the BACKLOG row.
- **Fixed:** a specific message for too few spline knots (above).
- **Fixed:** Python `set_rbf_parameters` checks the layer type before shapes, as
  before R1.
- **Fixed:** the read-only `size` property is defined only for derived-size families.
- **Documented in the contract:** `Layer.basis` and the vector attributes are copies,
  and configurations are unhashable.
