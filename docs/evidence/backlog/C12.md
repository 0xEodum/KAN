# Backlog C12: coalesced trainable-RBF center/log-width reduction

Date: 2026-10-14. Branch `cpp-foundation`, base `11a159d` (backlog M5 closed). Machine: GB10
(sm_121, 48 SMs, 24 MiB L2, 99 KiB opt-in shared memory per block, unified LPDDR5x), CUDA 13.0,
cuBLAS 13.1, GCC 13.3 ([port evidence](../port-aarch64.md)). Three Python processes of other
users held GPU contexts (15 GB) and were idle (0% utilization,
[gpu-before.txt](C12-bench/gpu-before.txt), [gpu-after.txt](C12-bench/gpu-after.txt)).

Finding (BACKLOG C12): `nonlinear_partial_kernel` reads `dx`, `dw` and `W` (the C2 scratch
`U*C`) by column, `terms` elements apart per lane. C1 replaced it for FP32 layers with at
most 85 terms (`nonlinear_staged_kernel`); FP64, and FP32/TF32 above 85 terms, still used it.

## Result

| | Change | Effect |
|---|---|---|
| FP64 | new `nonlinear_tile_kernel` (coalesced row chunks, shared-memory accumulators) with the summation order of the column kernel, selected per launch | reduction 2.71 → 0.44 ms per launch (256-wide, b2048, K=8); full `train_step` 0.86x (K=8, 32), 0.88x (K=16, 512-wide); **bitwise identical** (golden, step hashes, both builds) |
| FP32/TF32, > 85 terms | same kernel instead of the column kernel | full `train_step` 0.62x (FP32/TF32 256-wide K=96), 0.84x (64-wide K=96); bitwise identical |
| FP32/TF32, ≤ 85 terms | unchanged (C1 staged kernel, measured as fast as or faster than the tile kernel) | unchanged, bitwise |

No measured configuration is slower (worst 1.001, within noise). Untouched kernels are SASS-identical,
no arena memory is added, and no tolerance or default changes.

## Baseline and profile (RED)

Performance item: the failing state is the measured baseline and the profile.
Correctness RED: the new suite does not compile against `11a159d` (no reduction test hook,
[C12-red.log](C12-red.log)).

**Share of the step** (Nsight Systems, CUDA-graph nodes traced, FP64 trainable RBF
256x256x256x10, b2048, K=8, i.e. the port's `rbf-256x256x256x10-b2048` case,
[nsys/](C12-bench/nsys/)): three DGEMMs 64%, `nonlinear_partial_kernel` **16.8% (2.71 ms per launch,
3 launches per step, 8.1 ms of 48 ms)**, `basis_kernel` 12.7%, `backward_finish_kernel` 2.6%.
FP32 (same network): `nonlinear_staged_kernel` 24.5% at 0.245 ms per launch, about 205 GB/s for
its 50 MB of input, close to the device's measured copy rate (243-246 GB/s,
port evidence). ncu counters need admin rights on this machine (`RmProfilingAdminOnly: 1`,
no passwordless sudo), so sectors per request were derived and measured indirectly:

- At FP64 K=8 a row holds 64 contiguous bytes, so a warp's column load touches 32 sectors for
  256 useful bytes (4x overfetch); the K column blocks of a tile could share those sectors in
  L2 only while resident together. The grid (K x tiles = 512 blocks for K=8) exceeds what
  fits at once (288 blocks: 6 per SM on 48 SMs, `cudaOccupancyMaxActiveBlocksPerMultiprocessor`,
  [occupancy.cu](C12-bench/occupancy.cu), [occupancy.txt](C12-bench/occupancy.txt)) and the three 32 MiB tensors exceed the
  24 MiB L2, so each term's blocks re-read the rows from DRAM.
- Microbenchmark ([nl2.cu](C12-bench/nl2.cu), [microbench.csv](C12-bench/microbench.csv); the
  pre-C12 kernel verbatim as `column`, the C1 kernel as `staged`, best of 5x20 launches):
  effective input bandwidth of the column kernel at 524 288 rows collapses from 260 GB/s (K=4,
  256 blocks, resident together) to **44 GB/s at K=8** and 33-35 GB/s at K=32-96 (FP32 above 85
  terms: 16.5 GB/s at K=96). With 131 072 rows (K=8, 25 MB, just above L2) it gets 126 GB/s, and
  with 65 536 rows (13 MB, inside L2) 423 GB/s: the loss comes from re-reading data that does
  not fit in L2.

## Design

**Order to preserve.** For term k and tile t (`tiles = min(64, ceil(rows/256))`, unchanged),
lane l of the column kernel sums rows `t*256 + l + n*tiles*256` for n = 0, 1, ... in order
(`c += w*(-dx)`, `v += w*dw`), a shared-memory tree pairs lanes `l` and `l+step` for step =
128..1, and `nonlinear_finish_kernel` sums the tiles in order.

**`nonlinear_tile_kernel`** (`src/backends/cuda/resident.cu`). One block of 256 threads per
(tile, group of g consecutive terms). It holds the 256·g chains of the column kernel as
shared-memory accumulators at item `lane*g + j`. For each of the tile's 256-row chunks, it reads
the g values of every row (one contiguous 256·K-value range per tensor when g = K) with
consecutive threads on consecutive addresses, and each thread updates the items it owns (the
same thread for every chunk, so no synchronization is needed in the loop). Then it runs the same
tree per term and writes the same `partial[k*tiles + t]` layout, so `nonlinear_finish_kernel` and
the partials buffer are unchanged. Every addition has the same operands in the same order, so
the results are bitwise those of the column kernel. In the FMA build `c + w*(-dx)` contracts to
the same `fma` whether `c` is in a register or in shared memory (measured: microbenchmark built
with `--fmad=true`, full-step hashes in the FMA build, golden FMA dump).

**Groups (from device properties).** Shared memory per block is `2*256*g*sizeof(T)`. g = K
when that fits `cudaDevAttrMaxSharedMemoryPerBlockOptin` (GB10: K ≤ 24 FP64, ≤ 49 FP32),
otherwise the largest multiple of 128 bytes of terms that fits (16 FP64 / 32 FP32 on GB10), so
segments are whole cache lines when K is a multiple of it. This was measured better than
balanced groups: FP64 K=64 3.71 ms (g=16) vs 4.67 ms (g=22), K=96 5.33 vs 5.59 (g=24) and
6.87 ms (g=22); FP32 K=96 2.96 ms (g=32) vs 3.30 ms (g=48). Above 48 KiB the kernel's
dynamic shared-memory attribute is set at construction (before any graph capture), as C5 does.
The device query (`ExecutorDevice`, formerly `SplineDevice`, same fields) now also runs when
the network has a trainable-RBF layer.

**Selection (per launch, host).** FP32/TF32 layers whose rows fit the C1 stage keep
`nonlinear_staged_kernel`: it matches or beats the tile kernel at every measured shape (e.g.
524 288 x 8: 191 vs 192 us; 524 288 x 32: 0.88 vs 1.26 ms; 16 384 x 8: 4.5 vs 7.4 us), and
replacing it would change FP32 results. Every other layer takes the tile kernel when its grid
(groups x tiles) has at least `min(SMs, 64)` blocks (`cudaDevAttrMultiProcessorCount`; 64 =
`nonlinear_tiles`, the most tiles there can be, so that devices with more than 64 SMs still use
it for single-group layers), and otherwise the column kernel. Below that threshold the few tile blocks each serialize K times more work.
On GB10 the tile kernel is 2-5 us slower at 512-4096 rows (fixed latency), while the column
blocks are then few enough to be resident together and share the rows in L2. Because the two
kernels give the same bits, the choice affects only time. A rule on residency (K x tiles above
the resident column blocks) was also considered. Neither rule is right for every kernel-level
shape. Known misses of the adopted grid rule in [microbench.csv](C12-bench/microbench.csv), FP64:
- it picks the column kernel at 2048 x 64 (16.4 vs 14.4 us) and at 8192 x 16 (16.4 vs 14.4 us);
- it picks the tile kernel at 524 288 x 1 (22.4 vs 20.5 us) and at 524 288 x 3 (133.6 vs 130.5 us).

The residency rule would get the first two right, but it misses 131 072 x 4 (column 30.0 vs
tile 22.6 us) and the 65 536-row K=8 case (one block per SM is not the issue there). Each miss
costs at most about 2 us per launch. The grid rule was kept because it is simpler and depends
only on the SM count, and the full-step sweeps below show no configuration slower than before.

**Not changed.** `nonlinear_tiles`, the partials layout and `nonlinear_finish_kernel` stay as
they are (changing them would change the summation order). FP64 `basis_kernel` (unstaged rows; 12.7% of the
FP64 K=8 step before C12, 15.0% after) stays as C1 deliberately left it (FP64 staging cost the m2 Gaussian
RBF cases 1.9x on GA102). That is outside C12 and noted as a follow-up observation. FP32 steps with
more than 85 terms are now bound by the unstaged FP32 `basis_kernel`/`backward_finish_kernel`
rows (C1/C3 limit of 85 terms), not by the reduction.

**Test hook** (`src/backends/cuda/resident_testing.hpp`): `NonlinearReduction {Automatic,
Column, Tile}` and `ResidentTestScope(NonlinearReduction, ResidentLayout*)` force the column or
tile kernel for every trainable-RBF layer in every precision, including where FP32 would take
the staged kernel. `ResidentLayout::reduction_groups` reports each layer's tile-kernel group
(0 when the tile kernel is unavailable).

## Tests

New `tests/backends/cuda/local_rbf_reduction_resident_test.cpp` (CTest
`local_rbf_reduction_resident`, labels `cuda;local`), 3 cases:

- `column_and_tile_reductions_are_bitwise_equal`: FP64, FP32 and TF32. Two-layer trainable-RBF
  networks with 185 rows (less than one chunk), 16 800 rows (64 tiles, partial last chunk),
  K = 1, 3, 8, 70 and 90 (several groups with a short last one: FP64 16+16+16+16+6, FP32
  32+32+6 and 32+32+26; K=90 also takes FP32 past the C1 stage). Each executor is forced
  column or tile and runs eager forward + backward (L2) + SGD and two captured `train_step`s,
  at the full batch, a partial batch and an empty batch. Each forced tile executor must
  report a nonzero group, and at 70 and 90 terms fewer terms per group than the layer has, so
  the comparison cannot degenerate into the column kernel against itself. The case requires bitwise equal outputs,
  every gradient (input, coefficients, bias, centers, log widths) and every trained parameter.
  Where the staged kernel does not apply, the automatic choice must also match the forced column
  kernel bitwise.
- `tile_reduction_matches_cpu`: forced tile against the FP64 CPU (FP64 resident tolerance
  `1e-11|e| + 1e-12 max|e|`).
- `overflow_is_reported_and_recovered_under_either_path`: an overflowing upstream raises
  `overflow_error` under either forced kernel (FP64, FP32), and the executor recovers. Other
  kernels of the same step also report the overflow, so this case does not isolate the
  reduction kernel's own `report` calls. Those calls mirror the column kernel's: the lane sums,
  the tree results and, in `nonlinear_finish_kernel`, the final sums.

Mutations ([mutation.txt](C12-bench/mutation.txt)): ignoring the group offset k0 fails the
K=70 shape, and reading one row past a partial chunk fails the partial-batch shape.

| Check | Result |
|---|---|
| CTest CPU-only (`build-cpu`, Python) | 31/31 ([log](C12-bench/ctest-cpu.log)) |
| CTest CUDA parity (`build-cuda`, `KAN_CUDA_FMA=OFF`) | **51/51** (50 + `local_rbf_reduction_resident`) ([log](C12-bench/ctest-cuda-parity.log)) |
| CTest CUDA FMA (`build-cuda-fma`) | **51/51** ([log](C12-bench/ctest-cuda-fma.log)) |
| compute-sanitizer memcheck (leak check), racecheck, synccheck, initcheck on the new suite, both builds; memcheck on `local_resident`, `resident_training`, `input_map_resident`, `cuda_test`, `resident_precision` (parity) | 0 errors, 0 hazards, 0 leaks ([sanitizers.txt](C12-bench/sanitizers.txt)) |
| Golden (8 dumps: default, `--layers`, C3 FP32, C6-C8 rational; parity and FMA) | **byte-identical** to the M5 reference ([golden-sha256.txt](C12-bench/golden-sha256.txt) = `M5-bench/golden/sha256-linux.txt`) |
| SASS (`cuobjdump`, [C5 sass_cmp.py](C5-bench/sass_cmp.py)) | all 178 pre-C12 kernels instruction-identical in both builds; 2 new (`nonlinear_tile_kernel<double/float>`) ([sass-identity.txt](C12-bench/sass-identity.txt)) |

The golden fixtures are small and take the column kernel. Bitwise identity at shapes that take
the tile kernel comes from the full-step hashes below, which cover all parameters including
centers and log widths, and from the forced-path suite.

## Independent review

A fresh reviewer agent read the diff and the evidence and re-ran the new suite. It found
nothing blocking: the kernel's order, indexing, races and bounds, the selection, the
pre-capture shared-memory attribute, the failed-query fallback and the >64-SM threshold were
all confirmed, and so were the evidence tables (ABBA, rule sweep, nsys, golden, SASS,
sanitizers, CTest).

| Finding | Resolution |
|---|---|
| Four evidence numbers did not match the CSVs (131 072-row and 65 536-row bandwidths, 131 072 x 4 times, a wrong claim that the residency rule loses at 2048 x 64, and the `basis_kernel` share quoted only from before C12) | Corrected from `microbench.csv` and `nsys/`; the grid rule's known kernel-level misses are listed in Design |
| The bitwise test could not tell whether the tile kernel actually ran | `ResidentLayout::reduction_groups` added; the test requires a nonzero group and several groups at 70 and 90 terms |
| The nonfinite case does not isolate the reduction's reports | Renamed `overflow_is_reported_and_recovered_under_either_path`; its limits are stated in Tests |
| Nits: `<algorithm>` include, CONTRACT line break, the test-hook header note, the unmentioned basis cpu_full 0.470 outlier | Fixed / noted |
| Not changed: occupancy at 96 KiB on sm_86, 64-bit `i/g` (the kernel runs at copy rate) | Covered by the >64-SM open point / no measured cost |

After the fixes (host code and test only): CTest parity 51/51, FMA 51/51, kernels still
SASS-identical (178 + 2 new).

## Open points for the owner

- Devices with more than 64 SMs (e.g. the RTX 3090's 82) are unmeasured: there the tile kernel
  is chosen from 64 blocks (the most tiles), so some SMs stay idle during the reduction. C1's
  3090 profile, where the 64-block FP32 staged kernel cut the same reduction from 3.78 to 0.77
  ms, suggests 64 blocks suffice, but this was not measured with the tile kernel.

## Contract

`docs/CONTRACT.md` gains the paragraph "Trainable-RBF center/log-width reduction (backlog
C12)". It records the fixed summation order, the two kernels computing it bitwise, the per-launch
choice, the unchanged FP32 staged kernel, and no added arena memory. No tolerance, default or
public API changes. The test hook is private (`src/backends/cuda/resident_testing.hpp`, not
installed).
