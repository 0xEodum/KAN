# C1 + C10: resident precision policy and FMA build option

Backlog items C1 (P0) and C10 (P2), stage B, bundled per the status journal. Date: 2026-10-05,
branch `cpp-foundation`. Baseline: C2 (`build-b-c2`, sources of `2598368`; the R7 merge
`c1cdb0a` changed only the deprecated M1 adapter). This changes the public resident API, adds
a CMake option and defines new numerical tolerances; recorded here as `AGENTS.md` rule 5
requires. Defaults are unchanged, as decided by the owner through the coordinator: **the
executor stays FP64 by default**, FP32 is opt-in, the default build stays the parity build.
The owner had already accepted tolerance-based CPU/GPU parity and the cuBLAS dependency (C2).

## Change

### API and contract (C1)

- `kan::cuda::Precision { Float64 (default), Float32, TensorFloat32 }` in `kan/resident.hpp`;
  `ResidentNetwork(network, capacity, precision = Float64)`, `precision()`. Source compatible:
  every existing call (including the R7 adapter `src/cuda.cu`, not modified) builds an FP64
  executor. Python: `kan.Precision.FLOAT64/FLOAT32/TF32` (declared in every build, the header
  has no CUDA dependency), `kan.ResidentNetwork(network, capacity, precision=...)`,
  `ResidentNetwork.precision`. NumPy arrays stay strict float64.
- The host interface stays `double` for every precision. Uploads round to the executor
  precision; downloads widen exactly, so a downloaded FP32 network holds FP32-representable
  parameters.
- FP32 rejects with `std::invalid_argument` (before any device change) finite FP64 data or
  configuration it cannot represent: magnitudes above `FLT_MAX` (inputs, upstreams, parameters,
  centers, knots, shifts, gains, learning rate, L2 weight), positive quantities that round to
  zero (widths, scales, frequency, epsilons, tanh scale, exponentiated RBF log widths, learning
  rate), affine scales that round to zero, Jacobi `alpha/beta` that round to `-1`, distinct
  B-spline knots that round to one value. Values below the FP32 range round like any value.
- Nonfinite results are reported as before (`std::overflow_error`); a result beyond `FLT_MAX`
  is nonfinite in FP32 although finite in FP64. Log-space tails use the FP32 normal range.
- Guarded rational poles: FP32 uses the relative threshold `max(epsilon, n*2^-23)`, `n` the
  denominator degree. Horner evaluation of `Q` in FP32 has a rounding error of about
  `2n*2^-24` of the guard bound `1 + sum |b_k z^k|`, so below that `|Q|` is not distinguishable
  from a pole; the FP64 default `epsilon = 1e-8` is below FP32 resolution. FP32 therefore
  reports poles that FP64 accepts (tested at `|Q|/bound = 5e-8`).
- Tolerances (the suite's, per entry, against the FP64 CPU evaluated at the executor's own
  parameters): FP32 `|a-e| <= 2e-4|e| + 5e-5 max|e| + 1e-37`, TF32 `1e-2|e| + 1e-2 max|e|`.
  Trajectories over several SGD steps are compared against an FP64 trajectory within
  `1e-2|e| + 1e-3 max|e|` (TF32 floor `1e-2`), because SGD amplifies rounding (the wide C2
  network at rate 0.2: per-call 2e-5 grows to 3e-4 in three steps); that is sensitivity of the
  trajectory, not a per-call error.
- `TensorFloat32` is `Float32` with `cublasSetMathMode(CUBLAS_TF32_TENSOR_OP_MATH)`: GEMM
  operands rounded to 10 mantissa bits, FP32 accumulation; the kernels are the FP32 ones.
- BF16 was not implemented: it would need a third storage type and mixed-precision
  accumulation through every kernel, and TF32 already covers the tensor-core GEMM path (see
  measurements); not cheap, so skipped as the task allowed.

### Implementation

- Shared formulas (`src/detail/basis_formulas.hpp`, `rational_formulas.hpp`,
  `input_map_formulas.hpp`) are templates over `Scalar`; `BasisView`, `BasisRow`,
  `RationalHorner`, `RationalEdge` are aliases of the `double` instantiations, so CPU call sites
  are unchanged. Literals are `Scalar(...)`, so the float instantiation never promotes to double
  and the double instantiation performs the same operations as before. `host_device.hpp` adds
  float overloads (device: explicit `expf`, `logf`, ... ) and per-type constants
  (`constants<Scalar>::min_normal`, `ln2`). Rational formulas take any configuration type with
  `numerator_degree, denominator_degree, center, scale, epsilon` (`RationalConfig` on the CPU,
  `RationalScalars<T>` on the device).
- `src/resident.cu`: every kernel, plan, the context and the engine are templates over the device
  scalar `T`; `Engine<double>` and `Engine<float>` implement a precision-independent
  `ResidentExecutor` interface held by `ResidentNetwork::Impl`. cuBLAS calls go through overloads
  (`cublasDgemm_64`/`cublasSgemm_64`, `Dgemv/Sgemv`, `Dscal/Sscal`). Configuration scalars are
  converted and validated at plan construction (host, before allocation).
- FP32-only performance work (profiling below): row tiles staged through shared memory in
  `basis_kernel`, `backward_finish_kernel` and a new `nonlinear_staged_kernel` (trainable-RBF
  center/log-width reduction); a page-locked staging buffer for the per-step input/upstream
  uploads, filled by a single validating conversion pass; FP32 small-kernel thresholds.
- FP64 is the C2 executor: same kernels, access patterns, thresholds and summation order. The
  parity-build golden dump is **byte-identical** to C2.

### C10: `KAN_CUDA_FMA`

CMake option `KAN_CUDA_FMA` (default `OFF`; `scripts\build.ps1 -CudaFma`). `OFF` = parity
build, `--fmad=false` as before (the CPU's unfused intermediates; required for the bitwise
golden comparison). `ON` = performance build, nvcc's `--fmad=true`. Both builds pass the whole
suite. In the performance build an overflowing intermediate product can be cancelled inside an
FMA without being reported (already true of cuBLAS); `cuda_preserves_unfused_intermediate_overflow_contract`
still passes there only because the warp kernel accumulates its two products in different lanes.
The default stays the parity build (existing behaviour); the measured gain of FMA is limited to
FP64-kernel-bound steps (below), so making the performance build the default is an owner
decision, not needed for C1.

## Tests

New `tests/resident_precision_test.cpp` (RED in `1e74739`, [C1-red.log](C1-red.log): it did not
compile, no `kan::cuda::Precision`), 11 cases:

- default precision is FP64, explicit values reported, unknown enumerator rejected, FP64 accepts
  data beyond the FP32 range;
- all nine basis families between affine, trainable LayerNorm and tanh maps; high-degree
  Chebyshev/Legendre (12), Jacobi (10, alpha 2.5 beta -0.7; 9, alpha+beta = -0.95), Hermite (8);
  rational edges of all three policies and degrees (0,0) (0,3) (4,1) (3,2); the wide C2 network
  and the contraction paths (64->80 + 80->3 at batch 1000/400/7, and a 64->64 layer crossing both
  FP32 thresholds) - forward, backward with L2, SGD over 2-3 steps, every gradient tensor,
  trained parameters, allocation count;
- TF32 contractions within the TF32 tolerance and different from FP32 SGEMM (math mode active);
- overflow beyond `FLT_MAX` in forward, input VJP and SGD candidates is reported, SGD commits
  nothing, the executor recovers; learning rate / L2 beyond FP32 rejected;
- unrepresentable data and 12 configurations rejected in FP32 and accepted by FP64;
- log-space tails: Gaussian (fixed and trainable) whose value underflows FP32 keeps its
  6.2e-22 input derivative; Mexican hat whose `A/scale` overflows FP32 keeps its 6e21 derivative;
- guarded pole at `|Q|/bound = 5e-8`: FP64 accepts, FP32 raises `domain_error`, recovers;
- empty batch with L2, parameters stored as FP32-rounded values, allocation count equal to FP64, move.

`tests/precision_python_test.py` (4 cases, CUDA cases skipped without CUDA): enum, default,
FP32 training against the CPU, strict float64 arrays and the FP32 range check through Python.

## Benchmarks

GPU state: the first measurement rounds ran next to an external CUDA job (another project's
Python process at about 50% utilization; those numbers are not used). The final round
(15:13-15:23) had no other compute process; the desktop compositor still used 9-38% of the
GPU ([gpu-before.txt](C1-bench/gpu-before.txt), [gpu-after.txt](C1-bench/gpu-after.txt)), so
absolute times are a few percent above an idle GPU: C2's own FP64 steps measure 99 / 705 ms here
versus 96 / 690 ms in the C2 evidence. All rows of a table were measured in the same session.

**Large steps** ([large_step.cpp](C1-bench/large_step.cpp): forward + upload of the upstream +
backward + SGD, median of 7 (2 for 1024-wide), two rounds; Chebyshev K=7 unless noted; ranges
are the two rounds; PyTorch from `torch_reference.py` in the same session, which does not upload
an upstream per step):

| Topology, batch | C2 FP64 | C1 FP64 | C1 FP32 | C1 TF32 | PyTorch FP64 | PyTorch FP32 |
|---|---:|---:|---:|---:|---:|---:|
| 64->64->32->16, 1024 | 1.28-1.35 ms | 1.28 | **0.33-0.37** | 0.32-0.40 | 2.95 | 3.57 |
| 256->256->256->10, 8192 | 99.2-99.5 ms | 99.3-99.4 | **3.81-3.88** | 4.01-4.06 | 87.6 | 8.98 |
| 1024->1024->1024, 4096 | 701-708 ms | 699-717 | **27.4-28.6** | 23.3-25.7 | 582 | 22.3 |
| trainable RBF 256->256->256->10, 8192 | 116 ms | 115-121 | **5.4-5.8** | 5.4-5.5 | - | - |

FP32 against FP64: 3.7x (64-wide), 26x (256-wide), 25x (1024-wide), 21x (trainable RBF).
The FP32 and TF32 columns include both builds. The performance build (`KAN_CUDA_FMA=ON`) is
faster only where the FP64 kernels bound the step: FP64 64-wide 1.28 -> 1.03-1.06 ms; every
other row is within noise (GEMM bound, and cuBLAS fuses in either build).

**Fraction of the RTX 3090 FP32 peak** (35.6 TFLOPS: 82 SMs x 128 lanes x 2 x 1.695 GHz) for the
contraction work (three GEMMs of `2*batch*outputs*inputs*K` flops per layer: 46.0 GFLOP at
256-wide, 360.8 GFLOP at 1024-wide):

| Step | C1 FP32 | C1 TF32 | PyTorch FP32 |
|---|---:|---:|---:|
| 256-wide | 11.9 TFLOPS, **34%** | 11.4 TFLOPS, 32% | 5.1 TFLOPS, 14% |
| 1024-wide, full step | 13.0 TFLOPS, **36%** | 15.2 TFLOPS, 43% | 16.2 TFLOPS, 45% |
| 1024-wide, forward + backward + SGD | 20.5 TFLOPS, **58%** | - | (no upload in its protocol) |

The 256-wide FP32 step is 2.3x faster than PyTorch FP32. At 1024-wide the protocol's per-step
upload of the 4M-entry upstream costs 9.5 ms ([step_parts.txt](C1-bench/step_parts.txt): forward
6.2, upload 9.5, backward 11.1, SGD 0.3 ms), of which 5.2 ms is the PCIe copy (this machine
copies at about 3.2 GB/s, pinned). Without it the FP32 step is 17.6 ms against PyTorch's 22.3 ms.
Moving the loss gradient onto the device or overlapping the copy is C9 territory (fewer
synchronizations per step), not C1.

**TF32 decision.** [tf32_gemm.cu](C1-bench/tf32_gemm.cu) ([output](C1-bench/tf32_gemm.txt)): at
1024-wide TF32 runs the three GEMMs at 29-32 TFLOPS against 20-24 for SGEMM (1.3-1.5x); at
256-wide the coefficient GEMM (`dC = U^T Phi`, k = 8192) is 2x slower in TF32 (615 vs 312 us), so
the 256-wide step is not faster. TF32 also needs a 50x looser tolerance. It pays off only for
large square-ish contractions, so it is an opt-in precision, not the FP32 default.

**FP64 regression check (frozen suites, ABBA C2 vs C1 parity build, pooled median ratios,
geometric mean over cases; [summary.txt](C1-bench/summary.txt)):**

| Suite | CPU | Resident | Transfer |
|---|---|---|---|
| m2 | 1.037 | 1.018 (0.891-1.178) | 1.017 |
| m3 | 1.019 | 1.088 (0.852-3.470) | 1.078 |
| m4 (unchanged code) | 0.959 | 1.010 (0.942-1.230) | 0.982 |

The m3 maximum is one case (trainable RBF 64x64x32x16, batch 1024: 1.9 -> 6.5 ms with samples
spread 5.7-11.9 ms) during a transient; rerun alternately right after: C2 1.92 / 1.94 ms, C1
1.93 / 1.87 ms. The FP64 code path equals C2 (golden byte-identical), so the suites show noise.

## Profiling (AGENTS.md rule 6)

Nsight Systems kernel summaries of the final performance build for every step and precision are
in [nsys-kernels.csv](C1-bench/nsys-kernels.csv); Nsight Compute was used on the expansion kernels.

1. **Uncoalesced expansion rows (fixed).** First FP32 256-wide step (20.8 ms): `basis_kernel` 32%
   of GPU time (1.49 ms per launch), `backward_finish_kernel` 15% (0.81 ms), the SGEMMs 50%.
   Nsight Compute on `basis_kernel`: SM throughput 5.6%, DRAM 54%, flagged uncoalesced loads and
   stores: one thread per row of `K` contiguous values puts the lanes of a warp `K` elements
   apart. Staging tiles of consecutive rows through shared memory with coalesced copies: 1.49 ms
   -> 0.155 ms and 0.81 ms -> 0.153 ms per launch, at unchanged arithmetic and order.
2. **Trainable-RBF reduction (fixed for FP32).** `nonlinear_partial_kernel` was 44% of the FP32
   trainable-RBF step (3.78 ms per launch, column reads `K` apart). `nonlinear_staged_kernel`
   (coalesced tiles, fixed-order row-lane sum): 0.77 ms; the step went 37.6 -> 5.4 ms with item 1.
   This is the FP32 form of backlog C12, which stays open for FP64 (see below).
3. **FP64 kept unstaged (regression found and fixed).** The same staging in FP64 made the frozen
   m2 Gaussian RBF resident cases 1.9x slower (FP64-ALU-bound kernels lose occupancy to the
   32 KiB stage); staging is FP32-only and the FP64 executor is bitwise C2 again.
4. **Small shapes.** At 64-wide the C2 thresholds left FP32 work on the tiled kernels that SGEMM
   does faster. [small_shapes_f32.cu](C1-bench/small_shapes_f32.cu) ([output](C1-bench/small_shapes_f32.txt),
   quiet GPU): forward warp kernel wins up to about 14M multiply-adds (80x400x448: 22 vs 29 us;
   64x1024x448: 39 vs 20 us), so the FP32 forward threshold is 2^24; the tiled parameter VJP
   wins up to about 4M `batch*(coefficients+outputs)` (16x1024x224: 18 vs 23 us; 32x1024x448:
   39 vs 22 us), so FP32 adds a work bound of 2^22 to the 2^15 size bound. (A first round of
   these measurements ran under the external job and gave different crossovers; the thresholds
   use the quiet round.)
5. **Host upload (improved).** nsys showed 10-16 ms idle gaps before the upstream copy of the
   1024-wide step: pageable copy plus a 16 MiB temporary per call. A page-locked staging buffer
   (allocated at construction; host memory, not counted by `workspace_allocations()`) and one
   validating conversion pass: 15.2 -> 9.3 ms; the rest is the PCIe copy (5.2 ms) and the pass.
6. **What remains.** Final FP32 256-wide breakdown: three SGEMMs 70%, `backward_finish_kernel`
   15%, `basis_kernel` 9%; 1024-wide: SGEMMs 91%. The GEMMs are cuBLAS's choice (simt 128x64 /
   128x128 kernels, 15-24 TFLOPS in isolation); the remaining non-GEMM kernels are memory bound
   at the tensor sizes (C3, fused expansion, would remove the `Phi`/`Phi'` round trips).

## Decisions for the owner

- **Default build.** `KAN_CUDA_FMA` defaults to `OFF` (parity, as before). The performance build
  gains only on FP64-kernel-bound steps (FP64 64-wide: 18%) and nothing measurable in FP32; switching the default would change the FP64
  resident results within tolerance (2.3e-14).
- **FP32 guarded-pole threshold** `max(epsilon, n*2^-23)` changes which samples are reported as
  poles in FP32 relative to FP64; the alternative (keeping `epsilon`) would accept denominators
  that FP32 cannot resolve.
- **C12** is addressed for FP32 only (FP64 keeps the C2 kernel to stay bitwise C2); it stays open.

Resolved by the owner on 2026-10-06: **the default stays `KAN_CUDA_FMA=OFF`** (parity build),
and **the FP32 guarded-pole threshold `max(epsilon, n*2^-23)` is accepted**.

## Reproduction

```powershell
scripts\build.ps1 -Cuda -AllowUnsupportedCudaCompiler -Python -Benchmarks -Test -BuildDirectory build-b-c1
scripts\build.ps1 -Cuda -CudaFma -AllowUnsupportedCudaCompiler -Python -Benchmarks -Test -BuildDirectory build-b-c1-fma
# baseline: the C2 build (build-b-c2); in %TEMP%\kan-c1: golden_c2.txt / golden_c2_layers.txt and
# large_c2.exe compiled from golden.cpp / C2-bench/large_step.cpp against the C2 headers, then (Git Bash):
docs/evidence/backlog/C1-bench/run_all.sh build-b-c2 build-b-c1 build-b-c1-fma /c/Users/<user>/AppData/Local/Temp/kan-c1
```

`run_all.sh` runs the sanitizers, golden comparisons, ABBA frozen suites, the large steps in all
precisions for both builds, the PyTorch reference and the Nsight Systems summaries.
`small_shapes_f32.cu` and `tf32_gemm.cu` build with `nvcc -O3 -arch=sm_86 -std=c++20 <file> -lcublas`;
`step_parts.cpp` builds like `large_step.cpp`.
