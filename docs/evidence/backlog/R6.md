# R6: `.clang-format` and a formatted tree

Backlog item R6 (P2), stage B, pass 9 (M6 → R6). R6 came last so that one formatting pass
also covers M6's new code. Date: 2026-10-22, branch `cpp-foundation`, base `d354453` (M6
closed). Machine and builds as in [port-aarch64.md](../port-aarch64.md): Linux aarch64,
GB10 (sm_121), CUDA 13.0 (nvcc V13.0.88), GCC 13.3, CMake 3.28.3. Release builds
`build-cpu` (CPU-only + Python), `build-cuda` (parity, `KAN_CUDA_FMA=OFF`, Python,
benchmarks) and `build-cuda-fma` (performance build).

Finding (BACKLOG R6): dense lines with multiple statements, e.g.
`src/backends/cuda/resident.cu`, `src/carriers/rational/rational.cpp`.

R6 is a pure reformat plus enforcement. It changes no token outside whitespace, no
public header semantics, no contract and no default.

## Scope decision (AGENTS rule 5)

The backlog row names "M3/M4 code". The formatted scope is wider: every C, C++ and CUDA
source under `include/`, `src/`, `tests/`, `benchmarks/`, `examples/` and `python/`
(100 files).

- **Why the whole tree.** The dense style is not confined to M3/M4. Before the reformat,
  [dense-lines.txt](R6-bench/dense-lines.txt) counts 65 dense lines in `src/`, 137 in
  `tests/`, 7 in `benchmarks/` and 6 in `python/`. A partial format would leave two styles,
  and a check limited to some files cannot be stated simply. Library, tests and bindings
  are maintained together, so one rule ("the formatted tree") is what `check_format.sh`,
  CTest and CI can enforce.
- **Excluded: `docs/`.** The 50 evidence harnesses under `docs/evidence/` are records
  of the state they measured. Several are compiled against old private paths (see R4),
  and some are inputs to recorded results (the golden harness `golden/golden.cpp`).
  Reformatting them would rewrite evidence. `docs/.clang-format` (`DisableFormat: true`,
  `SortIncludes: Never`) keeps editor format-on-save off them too.
- **Not included.** CMake, shell, Python and Markdown files are not C/C++.
- **One deliberate layout** is kept with `// clang-format off/on`:
  `tests/core/layer_test.cpp`, where the coefficient vector is grouped per edge
  (`{0, 2, 0,  0, 0, 3, ...}`; formerly `{0,2,0, 0,0,3, ...}`). A search for column-aligned
  tables, grouped initializers and coefficient arrays found no other. The numerical
  constants (e.g. the Cody–Waite split in `src/init/portable_math.hpp`) are one per line;
  only trailing-comment alignment changed there. Gauss–Legendre rules are computed, not
  tabulated.

## Tool and version

clang-format **18.1.8**: the PyPI wheel `clang-format==18.1.8`, installed in the
project `.venv` (`.venv/bin/pip install clang-format==18.1.8`) and pinned in
`requirements-dev.txt`. `scripts/check_format.sh` looks in `.venv/bin` right after
`$CLANG_FORMAT`, and CMake's `find_program` uses it as a hint. There was no clang-format on this machine before (clang 18.1.3 is installed
without the formatter, and there is no sudo).

Version sensitivity ([versions.txt](R6-bench/versions.txt), each wheel's `--dry-run` over
the formatted tree):

| Version | Locations that would change |
|---|---|
| 17.0.6 | 140 locations in 19 files |
| 18.1.0, 18.1.3 (the version Ubuntu 24.04 packages, measured with the wheel), 18.1.8 | 0 |
| 19.1.7, 20.1.8 | 2 locations in 2 files |

The check therefore accepts any 18.x. For another major version it reports the version
and exits 77, which CTest records as *skipped* (`SKIP_RETURN_CODE 77`), not as failed.
It does the same when no tool is found or the configured one has gone.

## Enforcement

- `scripts/check_format.sh` runs `clang-format --dry-run --Werror --style=file` over the
  scope: git-tracked files plus new untracked, non-ignored ones that exist, or `find`
  outside a git checkout. It exits 1 with the offending locations, and 2 for a missing or
  invalid `.clang-format`. `--fix` rewrites in place. Tool lookup: `$CLANG_FORMAT`,
  `.venv/bin/clang-format`, `clang-format-18`, `clang-format`. It skips (exit 77) for no
  tool, another major version or bash older than 4; with `CHECK_FORMAT_STRICT=1` those
  cases fail instead.
- CMake registers CTest `format` (labels `format;build`, timeout 120 s, `SKIP_RETURN_CODE 77`)
  only for a top-level, non-Windows configuration where `find_program` finds bash and
  `clang-format-18` or `clang-format`. `NAMES_PER_DIR` with the hint `.venv/bin` means the
  pinned wheel there is preferred over PATH, as in the script. Without them no test is
  added and the configuration is unchanged. The CPU-only build has no new dependency.
  CTest counts grow by one where the tool exists: CPU 36 → 37, CUDA 59 → 60 against M6.
- CI: the coverage job of `.github/workflows/cpu.yml` installs `requirements-dev.txt`,
  so it gets clang-format 18.1.8. It now runs `CHECK_FORMAT_STRICT=1
  CLANG_FORMAT=clang-format bash scripts/check_format.sh` as its own step, which fails
  rather than skips when the tool is missing or the version is wrong. A skipped CTest
  `format` would show green, so this step closes that gap. CTest in the Linux jobs may
  also register `format` when the runner image provides a clang-format. A non-18
  version is skipped there; Ubuntu 24.04's 18.1.3 formats this tree identically.
  Windows jobs do not register the test.
- `.git-blame-ignore-revs` is meant for `git config blame.ignoreRevsFile
  .git-blame-ignore-revs`; GitHub reads it automatically. It is added in a follow-up
  commit with the formatting commit's full hash, because that hash does not exist
  before the commit. With only its comment lines, `git blame --ignore-revs-file` runs
  normally (checked).

## Verification

### Tokens: whitespace-only by construction and by check

[tokcmp.py](R6-bench/tokcmp.py) lexes every in-scope file at `d354453` and in the
formatted tree with clang's raw lexer (`clang -cc1 -dump-raw-tokens`, CUDA mode for
`.cu`, so `<<<`/`>>>` are single tokens). It compares the (kind, spelling) sequence of all
non-whitespace tokens. It also inserts an end-of-directive marker at each real newline
that ends a preprocessor line, so no token can move into or out of a `#define`,
`#pragma` or `#if`. Comments are compared with internal whitespace collapsed; the two
off/on markers are ignored. Escaped newlines count as whitespace. Inside directives two
positions where whitespace is significant are compared as well:

- between the name and `(` of `#define NAME(`, which decides function-like versus
  object-like (added after the review);
- inside `#include <...>`.

This covers what compiled-code identity cannot: macro bodies, `#if` branches not taken
here (MSVC, `__CUDA_ARCH__` host passes), tests and the consumer. One thing it does not
cover is whitespace inside a macro argument that the macro stringifies (`#x`). That
changes a string, and `objcmp.py` reports it below (`strings-ws`).

Result ([tokcmp.txt](R6-bench/tokcmp.txt)): **100 files, 280023 tokens and directive markers, whitespace-only**.
The launch tokens are unchanged per file (`resident.cu`: 61 `<<<`, 63 `>>>`; two of the
`>>>` close nested templates). The formatting commit changes nothing but whitespace,
apart from the two `clang-format off/on` comment lines.

Negative control ([tokcmp-negative.txt](R6-bench/tokcmp-negative.txt)): five deliberate
edits, all reported:

- a launch closer `>>>` written `>> >`;
- the `TEST` macro's last line moved out of the `#define`;
- one digit of a literal changed;
- `#include <cmath>` written `#include < cmath >`;
- `#define REQUIRE(expression)` written `#define REQUIRE (expression)`.

### Generated code

Two builds of each configuration (CPU, parity, FMA): `d354453` (A) and `d354453` with the R6
patch series applied (B). They use the same options and are built **at the same source
path**: one scratch worktree, A's build directories moved aside, then the patches applied
and B built. [codecmp.sh](R6-bench/codecmp.sh) compares, for every object file of the
build tree (library, tests, Python module, benchmarks, example):

- host code function by function with [objcmp.py](R6-bench/objcmp.py), which is R4's
  `objdiff.py` with string-pool relocations resolved to the strings they point at. It
  also compares the data sections byte for byte: every `.rodata*` except the string
  pools, `.data*`, and the CUDA fatbinary sections. This covers constant pools and
  tables (negative control: [objcmp-negative.txt](R6-bench/objcmp-negative.txt));
- the archives and the Python module with R4's `objdiff.py`, and byte for byte (`cmp`),
  listing the strings that contain any differing byte;
- every CUDA object per kernel with C5's `sass_cmp.py` (full kernels, as fixed in M7) and
  as whole SASS text.

Result ([codegen.txt](R6-bench/codegen.txt)):

| Build | Host objects | `libkan.a` | `libkan_cuda.a` | Python module | `resident.cu` SASS |
|---|---|---|---|---|---|
| CPU | 37 objects, 1225 functions: same instructions and data | byte-identical | — | byte-identical | — |
| parity | 66 objects, 3216 functions: same instructions and data | byte-identical | 726/726 functions identical | byte-identical | 292/292 kernels identical (1457088 lines) |
| FMA | 66 objects, 3216 functions: same instructions and data | byte-identical | 726/726 functions identical | byte-identical | 292/292 kernels identical (1410576 lines) |

Details:

- **Instructions.** Every host function and every kernel has the same instructions.
- **Stringified test expressions.** 22 functions (CPU build) and 35 (CUDA builds) are test
  functions whose `REQUIRE(expr)` stringifies the expression (`#expression`, the failure
  message). The formatter respaced those expressions, so the referenced string changes,
  e.g. `'grad.coefficients.size()==layer.coefficients().size()'` →
  `'grad.coefficients.size() == layer.coefficients().size()'`. Pool offsets move with them.
  `objcmp.py` classifies these as `strings-ws`: same instructions, and strings equal after
  removing whitespace. `TEST`/`REQUIRE` in `tests/support/test.hpp` are the only
  stringifying macros in the scope (checked by grep). No library code stringifies.
- **CUDA objects.** `resident.cu.o` and `cuda.cu.o` differ only in the `STT_FILE` symbol
  name, nvcc's temporary `tmpxft_<pid>_...cudafe1.cpp`. These are 6 bytes each; every
  differing byte of `libkan_cuda.a` lies in them. The Python modules, which link
  `libkan_cuda.a` and embed its fatbinary, are byte-identical.

The CTest builds were the main tree's `build-*`, at a different source path from the
scratch worktree. Compared with them (part 2 of codegen.txt), host instructions, data
sections and SASS are identical as above. The source path enters the names nvcc gives
anonymous-namespace and `_INTERNAL_` symbols, which the comparison normalizes. As a
result, the following differ as well:

- `resident.cu.o`'s compressed `.nv_fatbin`; its decompressed SASS is identical;
- the byte layout of `libkan_cuda.a`;
- the GOT slots of the CUDA builds' Python module (`ldr x3, [x3, #2800]` → `#2792`).

At the same path all of these are identical, as shown above.

So, for these builds (GCC 13.3 and nvcc 13.0 on aarch64), the reformat cannot change
results on any input. That is a stronger statement than the golden samples below. For
other compilers and platforms the token check above is the argument: their compiler
sees the same token stream.

## Reproduce

Repository root, Linux; `E=docs/evidence/backlog/R6-bench`; `F` = the in-scope files
(`git ls-files include src tests benchmarks examples python | grep -E '\.(c|cc|cpp|cxx|h|hh|hpp|hxx|cu|cuh)$'`).

```bash
.venv/bin/pip install clang-format==18.1.8        # or: pip install -r requirements-dev.txt
scripts/check_format.sh                            # exit 0; --fix formats
python3 $E/tokcmp.py d354453 $F                    # whitespace-only
python3 $E/dense_lines.py d354453 $F; python3 $E/dense_lines.py WORKTREE $F
# generated code: a d354453 worktree W with scripts/build.sh builds (--python; --cuda --python
# --benchmarks; --cuda-fma --python --benchmarks), move W/build-* to A/, apply the R6 patches
# in W, rebuild the same three, then for each b:
$E/codecmp.sh A/$b W/$b      # instructions, data sections, SASS, and cmp of archives/modules
for b in build-cpu build-cuda build-cuda-fma; do cmake --build $b -j20 && ctest --test-dir $b; done
scripts/golden_dumps.sh <out> parity=build-cuda fma=build-cuda-fma
```
